[작업 환경]
- 작업 폴더는 현재 디렉터리(/work)이며 이 과제가 끝날 때까지 남습니다. 처음에는 base_carter_run.py 원본이 들어 있습니다. 프롬프트에 실린 것과 같은 파일이므로 읽기만 하고 절대 고치지 마십시오. 작업 폴더 밖은 뒤지지 마십시오.
- 도구 호출 1회(이하 '셀')는 매번 새 Python 프로세스로 실행되므로 변수가 다음 셀로 이어지지 않습니다. 남는 것은 작업 폴더의 파일뿐이고 /tmp 는 셀이 끝나면 지워지므로, 모든 파일은 작업 폴더 안에 쓰십시오.
- 셀에 보낸 코드와 그 호출에서 한 생각은 다음 호출의 대화에 남지 않고, 셀의 출력만 남습니다. 실행한 셀 코드의 사본은 /work/.cells/ 에 번호순으로 남으니 필요하면 읽기만 하고 고치거나 지우지 마십시오. 그러므로 셀 출력은 그것만 보고도 무엇을 했고 결과가 어떤지 알 수 있게 쓰십시오. 첫 줄은 아래 셀 머리가 찍는 목적 줄이고, 마지막 줄은 '요약: 만들거나 바꾼 것 / 결과 / 다음 할 일' 한 줄입니다.
- 하네스는 출력 끝에 '[exit 종료 코드, 실행 초]'를 붙입니다. 셀 하나는 600초가 지나면 강제로 끝나고 '(시간 초과)'가 붙습니다. 출력(stdout과 stderr)이 8,000자를 넘으면 앞 4,000자와 뒤 4,000자만 돌아오므로, 요약해서 찍고 가장 중요한 줄은 맨 끝에 두십시오. 그림은 볼 수 없고 텍스트만 돌아옵니다.
- 대화가 길어지면 오래된 셀 출력부터 '[이전 실행 출력 생략: N자]'로 바뀌어 최근 6개 셀의 출력만 남을 수 있습니다. 결과와 결정은 파일에 남기고, 진행 상황을 알 수 없으면 scratch/notes.md 와 scratch/test_log.txt 의 끝부분을 출력해 이어 가십시오.
- 오래 걸리는 시험은 저장한 스크립트를 subprocess 로 [sys.executable, '-u', 스크립트, 인자…] 처럼 실행하고 timeout 은 450초 이하로 주십시오. stdout 과 stderr 를 함께 받아 출력하고, TimeoutExpired 가 나면 예외에 담긴 부분 출력(바이트일 수 있음)도 찍으십시오.
- 도구 인자는 {"code": "<파이썬 코드>"} 형태의 JSON 이어야 합니다. 형식이 틀린 호출도 1회로 셉니다.
- 답 하나를 내기까지 도구 호출은 최대 28회입니다. 28회를 다 쓰거나 그 답을 위한 작업을 시작한 지 6시간이 지나면 도구가 막히고, 도구 없이 바로 최종 답을 내야 합니다. 첫 셀을 실행할 때 이미 수십 분이 지났을 수 있습니다. 서로 의존하지 않는 일은 한 셀에 묶으십시오.
- 한 셀에 넣는 코드는 약 250줄 이하로 하십시오. 더 긴 파일은 여러 셀에 나눠 이어 쓰고(첫 셀은 'w', 이후 'a'), 나눠 쓰는 동안에는 셀마다 파일의 줄 수와 마지막 몇 줄을, 다 쓴 뒤에는 ast 로 파싱해 정의된 함수 이름과 인자 목록을 출력하십시오.
- 처음 답을 낼 때의 셀 배분 예: 1 셀 머리·환경 확인·설계 메모 / 2–4 컨트롤러 코드 / 5–6 시뮬레이터 / 7 조립·검사, 첫 주행, 임시 제출 / 8–10 시험 묶음, 고장 시험, 결정성·정적 점검 / 11–20 분석·수정·재시험 / 21–22 통독과 마지막 수정 / 23–25 전체 회귀 / 26 최종 확인 / 27–28 예비.

[셀 머리]
첫 셀에서 scratch/ 를 만들고 scratch/head.py 를 아래 내용 그대로 저장하십시오. 첫 셀은 저장한 바로 다음 줄에서, 이후 모든 셀은 첫 줄에서 PURPOSE = '<이 셀로 무엇을 왜 하는지 한 줄>'; exec(open('/work/scratch/head.py').read()) 를 실행합니다. 다시 제출하라는 요청을 받은 뒤의 첫 셀에서만 이 줄 앞에 NEW_ANSWER = True 를 두십시오. head 가 찍는 셀 번호로 도구 호출 수를 셉니다. head 를 빠뜨린 셀이나 형식이 틀린 호출은 세지 못하므로 그만큼 여유를 두십시오.
```python
import sys, json, time, pathlib
sys.stdout.reconfigure(line_buffering=True)
if '/work/scratch' not in sys.path:
    sys.path.insert(0, '/work/scratch')
_p = pathlib.Path('/work/scratch/budget.json')
_b = json.loads(_p.read_text()) if _p.exists() else {'answer': 0}
if globals().get('NEW_ANSWER') or _b['answer'] == 0:
    _b = {'answer': _b['answer'] + 1, 'cell': 0, 't0': time.time()}
_b['cell'] += 1
_p.write_text(json.dumps(_b))
print(f"[답 {_b['answer']} · 셀 {_b['cell']}/28 · 첫 셀부터 {(time.time() - _b['t0']) / 60:.0f}분] 목적: {globals().get('PURPOSE', '?')}")
```

2. 컨트롤러 코드(scratch/region.py) — EDIT REGION 의 시작 표식 줄('# [EDIT REGION]' 으로 시작하는 줄)과 끝 표식 줄('# ========================= [END EDIT REGION]' 으로 시작하는 줄) 사이에 넣을 코드만 이 파일에 씁니다. 두 표식 줄은 assemble.py 가 base 에서 그대로 가져옵니다.

3. 시뮬레이터(scratch/sim.py) — numpy 로 간단한 시뮬레이터를 직접 만들어 컨트롤러를 시험합니다.
 ① 첫머리에 '실제 채점 환경이 아님'을 적고, 들어간 값마다 입력에서 온 것과 지어낸 것을 구분해 적으십시오.
 ② 시험 대상은 조립된 파일입니다. 파일 텍스트에서 실제 채점 환경을 불러오거나 실행하는 부분(그 환경에만 있는 모듈의 import 와 그것을 쓰는 실행 코드)만 코드로 걸러 내고, 나머지를 허용된 표준 모듈과 함께 exec 해 거기서 컨트롤러를 꺼내 쓰십시오. 컨트롤러 코드를 시뮬레이터용으로 따로 베껴 두지 마십시오.
 ③ 로봇은 과제가 정한 호출 주기로 적분하는 단순 운동학 모델로 만들고, 명령이 바로 반영되지 않는 응답 지연을 매개변수로 두십시오. 매 주기 '컨트롤러 호출 → 운동 적분 → 충돌 판정' 순서를 지키십시오.
 ④ 센서 함수는 base 문서에 적힌 이름·인자·기본값·반환 형식을 그대로 따르게 만들어, 컨트롤러를 고치지 않고 그대로 부를 수 있게 하십시오. 문서가 정하지 않은 부분(빔 순서, 각도의 부호 방향, 센서 원점 등)은 가정으로 적으십시오.
 ⑤ 입력이 준 장애물은 문서의 단위와 좌표 정의대로 시험 세계에 넣으십시오.
 ⑥ 프롬프트가 존재만 말하고 위치·크기를 주지 않은 구조물은 그럴듯한 형태로 지어내되, 한 가지 추측에 맞추지 말고 위치·방향·크기를 바꾼 여러 배치로 시험하십시오. 스스로 정한 환경 가정값도 매개변수로 두어, 가정이 틀린 경우로도 시험하십시오.
 ⑦ 모르는 요소는 켜고 끄는 스위치로 두십시오: 로봇 크기와 자세 기준점 위치, 응답 지연, 속도·각속도 상한, 아주 작은 회전 명령 무시, 각도 부호 반대, 각도 단위가 도, 센서 원점이 자세 기준점과 다름, 센서 호출 예외. 컨트롤러의 방어 코드마다 그것을 실제로 발동시키는 스위치가 있어야 합니다. 무작위성은 시드로만 만드십시오.
 ⑧ 충돌은 매 주기 차체 외곽 다각형과 장애물의 겹침으로 보수적으로 판정하고(조금이라도 겹치면 충돌), 장애물별 접촉 시작의 횟수·시각·위치·상대를 기록하되 첫 접촉 뒤에도 끝까지 돌리십시오. 최소 여유거리와 그 상대, 경로 길이, 실행 시간도 기록하십시오.
 ⑨ 합격 판정에는 프롬프트의 성공 조건을 하나도 빼지 않고 그대로 쓰고, 시간 제한보다 조금 더 길게 돌려 초과 여부도 보십시오.
 ⑩ 시나리오마다 컨트롤러 상태를 새로 만들고, 주행 중에는 안쪽 함수를 직접 불러 예외가 드러나게 하십시오.
 ⑪ 시나리오마다 한 줄 요약(PASS/FAIL, 종료 시각, done 여부, 목표 거리, 방위 오차, 접촉 수, 최소 여유거리와 상대, 경로 길이, 실행 시간, 켠 스위치(무작위 묶음에서 시드로 정해진 변형 포함), 컨트롤러가 스스로 끈 기능이 있다면 그 상태)을 출력하고, 궤적(일정 간격의 자세와 컨트롤러 모드)을 돌려받을 수 있게 하십시오.
 ⑫ numpy 로 벡터화하고 먼 물체는 미리 거르십시오. 시나리오 1개의 실행 시간은 10초 이하를 목표로 하고, 30초를 넘으면 시험 묶음을 만들기 전에 시뮬레이터부터 빠르게 하십시오. 시뮬레이션 시간 상한과 시나리오당 실제 실행 시간 상한(60초, 넘으면 시간 초과로 기록하고 다음 시나리오로)을 두십시오.
 ⑬ 텍스트 그림 함수를 두십시오. 범위는 시험 세계의 경계에서 자동으로 잡고, 전체가 약 3,000자 안에 들도록 칸 크기를 정해 북쪽이 위로 가게 찍습니다. 문자 예: 경계 '#', 과제가 준 장애물 'B', 지어낸 구조물 'o', 빈칸 '.', 궤적 '*', 출발 'S', 목표 'G', 접촉 지점 'X'. 실패 지점 주변 몇 m 는 더 촘촘하게 따로 찍을 수 있게 하십시오.

4. 조립과 검사(scratch/assemble.py <출력 경로>) — base_carter_run.py 를 'rb' 로 읽어 두 표식 줄을 찾고, 시작 표식 줄까지(그 줄 포함)와 끝 표식 줄부터(그 줄 포함)는 base 의 바이트를 그대로 둔 채 그 사이만 region.py 의 내용으로 바꿉니다. EDIT REGION 밖 텍스트는 코드로만 옮기고 절대 다시 타자하지 마십시오. 다음을 검사해 결과를 출력하고, 모두 통과했을 때만 출력 경로에 쓴 뒤 다시 읽어 확인하십시오. ① 두 표식 줄이 각각 정확히 한 번 나옴 ② 시작 표식 줄까지와 끝 표식 줄부터가 base 와 바이트 단위로 같음 ③ 파일 전체가 compile() 됨(py_compile 은 __pycache__ 를 만들므로 쓰지 않음) ④ 블록을 ast 로 파싱해 import 문이 없음 ⑤ 블록에 금지된 기능(난수·벽시계·파일 입출력·스레드)에 쓰이는 이름(random, time, open, thread, os, sys, eval, exec, __import__ 등)이 없음 ⑥ difflib 으로 base 와 비교해 바뀐 줄이 모두 두 표식 줄 사이에 있음. 하나라도 실패하면 고친 뒤 다시 조립하십시오. 시험은 항상 방금 조립한 scratch/candidate.py 로 하고, 조립한 파일 전체를 그대로 실행하지 마십시오.

5. 첫 주행 — 입력이 준 정보만으로 만든 가장 단순한 세계에서 출발부터 종료 신호까지 전체 임무를 한 번 끝까지 돌리고, 일정 간격(예: 2초)으로 자세와 모드를 출력해 로봇이 실제로 목표까지 가서 멈추는지 확인하십시오. 가짜 센서값으로 함수를 한 번 불러 보는 것은 주행 시험이 아닙니다. 텍스트 그림도 한 번 찍어 보십시오. 이 주행과 4단계 검사를 통과한 첫 후보는 assemble.py 로 제출 파일로도 저장해 두십시오. 도구가 막힐 때를 대비한 것이며, 이후에는 검사와 시험을 통과한 후보로만 덮어씁니다.

6. 시험 묶음 — 시험 코드는 파일로 저장하고, 후보 파일 경로·시나리오 이름·시드 범위를 인자로 받아 다시 불러 쓰십시오.
 ① 고정 묶음(suite.py): 범주를 고루 넣으십시오. 장애물 배치 변형(경로 한가운데, 좁은 통로, 목표 주변), 센서 규약 변형(각도 부호 반대, 도 단위, 센서 원점 어긋남), 로봇 변형(차체가 가정보다 큼, 기준점 어긋남, 큰 응답 지연, 속도 상한, 작은 회전 명령 무시), 스스로 세운 환경 가정이 틀린 경우.
 ② 무작위 묶음(rand_suite.py): 프롬프트가 언급한 종류의 구조물과, 언급되지 않았지만 그런 장소에 있을 법한 다른 물체를 개수·위치·방향·크기를 바꿔 무작위로 놓되, 출발·목표 주변의 일정 거리와 다른 장애물과의 최소 간격을 지키는 배치만 받아들이고 정해진 횟수까지 다시 뽑으십시오. 일부 시드에는 센서·로봇 변형을 섞되 시드에서 정해지게 하십시오. 세계 생성 함수는 따로 두어 실패 재현에도 같은 함수를 쓰십시오.
 ③ 고장 시험(edge_tests.py): 공개 controller 에 센서 호출 예외, None 이나 형식이 다른 반환값, 이상한 거리값, 센서 객체 없음, NaN 자세, 첫 호출, 시간이 처음으로 되돌아감(재시작), 도달할 수 없는 목표를 주고, 예외가 밖으로 나오지 않는지, 충돌 없이 제한 시간 안에 멈추는지, 그때 어떤 기능이 꺼졌는지를 한 줄씩 출력하십시오.
 ④ 결정성과 시간: 같은 시나리오를 상태를 새로 만들어 두 번 돌려 매 주기의 (v, w, done) 이 완전히 같은지 비교하고, 컨트롤러 1회 호출 시간의 평균·중앙값·최대를 출력하십시오. 프롬프트대로 벽시계 속도는 판정에 쓰이지 않으므로, 이 값은 시험 한 번에 걸리는 시간을 가늠하는 데 씁니다. 시나리오가 느린 원인이 컨트롤러라면 같은 출력을 내는 범위에서만 계산을 줄이십시오.
 ⑤ 정적 점검: 린터가 없으면 ast 로 정의 없이 읽히는 이름, 쓰이지 않는 이름, 상태 객체에서 읽기만 하거나 쓰기만 하는 속성을 출력하십시오.
 ⑥ 모든 시험 결과를 scratch/test_log.txt 에 한 줄씩 덧붙이십시오(시각, 묶음 이름, 후보 파일과 그 sha256 앞 12자, 통과/전체, 실패 목록).
 준비한 시험이 모두 통과해도 바로 제출하지 말고, 아직 시험하지 않은 범주를 찾아 더하십시오.

7. 결과 읽기와 고치기
 - 실행 결과를 받으면 다음 코드를 쓰기 전에 notes.md 의 진행 기록에 세 가지를 한두 줄로 적으십시오: 무엇이 실패했나, 원인 가설은 무엇인가, 어떤 출력으로 그 가설을 확인할 것인가.
 - 원인은 증상에 맞게 다음을 확인해 가리십시오. 진단 출력이 맞는지는 늘 먼저 봅니다(이상해 보이거나 결과가 지나치게 좋거나 빠르면 원자료 숫자를 따로 세어 진단 코드의 문제인지부터 확인). 그다음 시나리오가 성립하는가(시작 자세에서 로봇이 이미 장애물과 겹치거나 닿아 있지 않은지, 목표가 막혀 있지 않은지, 출발에서 목표까지 로봇이 지나갈 길이 실제로 있는지를 시뮬레이터가 아는 실제 배치로 따로 확인), 수정이 실제로 적용됐는가, 같은 시드·같은 스위치로 재현되는가, 컨트롤러 결함인가·시뮬레이터 가정 탓인가·능력 한계인가.
 - 원인이 불분명하면 첫 접촉의 시각·장애물·자세, 그 직전 몇 초의 궤적·모드·명령, 실패 지점 주변의 촘촘한 텍스트 그림을 출력하고, 의심되는 내부 함수를 감싸 입력과 출력을 기록하십시오. 같은 시드에서 의심 요인 하나(스위치 하나나 매개변수 하나)만 바꾼 두 주행을 나란히 돌려 결과 차이를 출력하십시오. 로봇이 멈춰 버렸다면 그 자세에서 멈춤을 일으킨 조건과 그때의 내부 값을 출력하십시오. 원인을 한 문장으로 적고 확인하기 전에는 매개변수를 이리저리 바꾸지 마십시오.
 - 처리: 컨트롤러 결함은 고칩니다. 시험·시뮬레이터 결함은 시뮬레이터를 고치거나 기록합니다. 시작 자세가 이미 겹치는 등 성립하지 않는 시나리오는 비슷한 성립 변형으로 바꾸십시오. 가정한 가장 작은 차체 크기로도 출발에서 목표까지 길이 없는 배치만 '도달 불가' 시험으로 옮겨, 충돌 없이 제한 시간 안에 멈추는지 확인하십시오. 그 밖의 실패(좁은 틈 같은 능력 한계)는 묶음에 실패로 남겨 통과/전체에 그대로 세고 보고하십시오. 어떤 대응도 충돌 0 원칙을 깨면 안 됩니다.
 - 능력 한계가 의심되면 그 요인만 남긴 최소 시나리오를 만들어 값을 몇 단계로 바꿔 가며 한계를 재고, 경계 근처 값 몇 개는 고정 묶음에 남기십시오.
 - 통과한 시험도 살피십시오. 최소 여유거리가 가장 작은 2–3개는 텍스트 그림과 가장 가까웠던 순간의 시각·위치·명령을 보십시오. 판정 기준에 가깝거나 평소와 다른 수치가 보이면 원인을 확인해, 컨트롤러 동작이 원인이면(예: 로봇이 멈추기 전에 done 을 냄) 고치고, 일부러 받아들이는 것이면 그 이유를 notes.md 에 적으십시오. done 을 낼 때 로봇이 실제로 멈춰 있었는지 확인하고, 예외 처리로 어떤 기능이 조용히 꺼진 흔적도 찾으십시오.
 - 코드를 고칠 때는 앞선 셀의 코드가 대화에 남지 않으므로, 먼저 바꿀 부분의 현재 코드를 파일에서 출력해 읽으십시오(진단하는 셀에서 함께 출력하면 셀을 아낍니다). 그 출력에서 원래 문자열을 그대로 가져와 파일에 정확히 한 번 나오는지 assert 한 뒤 치환하거나, 함수 하나를 통째로 바꿀 때는 ast 로 그 함수의 시작·끝 줄을 찾아 새 정의로 교체하십시오. 같은 셀에서 다시 조립·검사하십시오. 상수나 함수를 바꾸기 전에는 그 이름의 사용처를 모두 검색해 출력하십시오. 출력에 Traceback 이나 AssertionError 가 있으면 그 셀의 시험 결과는 옛 코드의 결과이므로 버리고 수정부터 다시 하십시오. 도구 출력은 시험 결과보다 위에 있는 오류 메시지부터 읽으십시오. 바꾼 내용은 진행 기록에 한 줄로 남기십시오.
 - 예외 처리로 감싸기처럼 컨트롤러 구조를 크게 바꾼 뒤에는 region.py 전체를 9단계와 같은 방식으로 나눠 한 번 읽으십시오. 컨트롤러에 새 분기(예외 처리 등)를 넣으면 그 분기가 실제로 실행되는 시나리오를 시뮬레이터 스위치와 함께 추가하고, 실행됐는지 출력으로 확인하십시오. 한 번도 실행되지 않은 분기는 시험되지 않은 것입니다.

8. 재시험과 회귀
 - 고친 직후에는 실패했던 시나리오와 가장 단순한 시나리오만, 고친 것이 몇 개 모이면 고정 묶음 전체, 큰 변경 뒤와 제출 전에는 전체 회귀(고정 묶음 전부, 무작위 묶음, 고장 시험)를 돌리십시오. 도구 호출을 아끼도록 한 셀 안에서 '수정 → 조립·검사 → 표적 재시험 → 통과하면 고정 묶음'을 이어서 실행하십시오.
 - 먼저 시나리오 1개의 실행 시간을 재서 셀마다 돌릴 개수를 정하십시오(셀당 300초 이내). 큰 회귀는 여러 셀로 나누고, 결과를 test_log.txt 에 쌓아 다음 셀에서 이어 읽으십시오. 출력은 실패 줄과 '통과 a/b [실패 목록]' 합계만 찍고 합계는 맨 끝에 두십시오.
 - 수정에 참고한 무작위 시드와 별개로 한 번도 쓰지 않은 시드 범위를 남겨 두었다가, 큰 이정표와 제출 직전에 돌리십시오.
 - 여러 셀에 걸친 회귀 도중에는 시험 대상 파일을 바꾸지 마십시오. 바꿨다면 바꾼 파일로 처음부터 다시 돌리십시오. 마지막 코드 수정 뒤에는 반드시 전체 회귀를 한 번 더 돌린 다음에만 최종 답을 내십시오(5단계의 임시 제출은 예외).

# 본론 초안 — 프롬프트에 있어도 사용되지 않는다

대상: 대한임베디드공학회 추계학술대회 단편(4쪽). 서론은 저자 작성분을 그대로 두고,
2~5장과 결론 초안만 담는다. 모든 수치는 `REPORT.md` 의 실측에서 옮긴 것이고 출처
파일을 각 절 끝에 적었다. **철회된 주장 2건은 들이지 않았다**(아래 "쓰지 말 것" 참조).

## 2. 평가 환경

### 2.1 주행 환경과 성공 조건

평가 환경은 Isaac Sim 4.5.0 기반의 실내 창고 주행 과제이다. 로봇은
Nova Carter 차동 구동 플랫폼이며, 출발 자세 (−9.0 m, −10.8 m, 1.0138 rad)에서 출발하여
반대편 목표 자세 (8.0 m, 16.5 m, 1.0138 rad)에 도달해야 한다. 주행 경로 사이에는 정적
상자 14개와 창고의 고정 구조물(벽, 기둥, 선반, 지게차)이 놓여 있다.

생성된 코드는 `controller(t, pose, env) -> (v, w, done)` 계약을 따르며 60 Hz 로 호출된다.
`pose` 는 섀시의 물리 엔진 기준 자세이고, 반환된 전진 속도와 각속도는 ROS 2 `/cmd_vel`
토픽으로 발행된다. 판정은 생성 코드가 수정할 수 없는 고정 하네스가 수행한다. 성공 조건은
표 1과 같으며, 네 조건을 모두 만족해야 통과로 판정한다.

**표 1. 성공 조건**

| 항목 | 기준 |
|---|---|
| 최종 위치 | 목표로부터 0.75 m 이내 |
| 최종 자세 | yaw 오차 0.26 rad 이내 |
| 충돌 | 0회 |
| 제한 시간 | 120 s |

### 2.2 환경 명세와 센서 명세의 상호작용

본 환경의 핵심은 **환경 명세와 센서 명세가 별개의 문서에 기술되어 있고, 두 값을 함께
읽어야만 올바른 제어가 가능**하다는 점이다.

생성 코드에 제공되는 기반 파일은 상자 14개의 중심 좌표, 가로·세로 크기와 **높이**를 표로
명시한다. 이 중 4개 상자의 높이는 0.18~0.25 m 이다. 한편 같은 파일의 주석은 거리 센서의
기본 동작을 `raycast_scan(n_beams=61, fov_deg=180.0, z=0.35, max_range=6.0)` 으로 기술한다.
즉 센서는 바닥으로부터 **0.35 m 높이의 수평면**을 훑는다.

따라서 높이 0.18~0.25 m 의 상자 4개는 **센서 평면 아래에 위치하여 거리 센서에 전혀 검출되지
않는다**(그림 2). 이하 이를 **저평면 장애물**이라 부른다. 저평면 장애물을 회피하려면
(가) 명세의 상자 표를 읽어 지도 기반 장애물로 취급하거나, (나) 센서 평면을 상자 높이 아래로
낮추어야 한다.

**이 정보는 은닉되어 있지 않다.** 상자 높이와 센서 평면 값이 모두 생성 코드에 함께 제공되는
동일 파일 안에 평문으로 기술되어 있으며, 두 값의 대소 비교만으로 결론이 도출된다. 본 연구가
측정하려는 것은 정보의 은닉 여부가 아니라 **제공된 명세가 실제 제어 코드로 연결되는지**이다.

본 환경은 서로 다른 능력을 측정하는 두 트랙으로 구성된다. **트랙 A(계획)** 는 상자 표를
읽어 경로를 계획하는 것을 허용한다. **트랙 B(반응)** 는 좌표와 배치의 하드코딩을 금지하고
장애물을 센서로만 파악하도록 요구한다. 두 트랙은 측정 대상이 다르므로 수치를 직접 비교하지
않는다.

### 2.3 실험 조건

평가 대상은 공개 가중치 모델 3종(gpt-oss-120b, Qwen3-32B-FP8, EXAONE-4.0-32B-FP8)이다.
모델당 2개 트랙에 대해 각 5개 표본을 수집하여 총 30건을 얻었으며, 동일한 조건을 두 가속기
환경(NPU: Furiosa RNGD 4장, GPU: NVIDIA RTX PRO 6000 Blackwell 1장)에서 반복하여 **총 60건**을
수집하였다. 양쪽 환경은 동일한 가중치와 동일한 양자화를 사용하였고, 재배포 체크포인트의
해시가 상류 배포본과 일치함을 확인하였다.

모델 입력은 **트랙 프롬프트와 기반 파일 두 개뿐**이며, 그 외의 시스템 프롬프트, 도구 호출,
오케스트레이션 지시는 제공하지 않는다. 샘플링은 temperature 0.7, top_p 0.95 로 고정하였다.
**가속기 환경의 차이는 본 연구의 주장이 아니라 통제 조건이다** — 생성 결과의 차이가 서빙
백엔드가 아니라 모델에서 비롯되는지 확인하기 위한 것이다.

### 2.4 정적 검증과 물리적 실행의 간극

수집된 60건에 대해 먼저 정적 검증을 수행하였다. 검증 항목은 (i) 구문 분석 성공,
(ii) 지정된 수정 구역 외부가 기반 파일과 바이트 단위로 동일한지, (iii) 트랙 B 의 경우 배치
하드코딩 금지 규칙 준수 여부이다. (iii)은 파이썬 토크나이저로 문자열과 주석을 분리하여
검사하므로 주석 안의 문자열이 오탐을 일으키지 않는다.

**정적 검증 결과는 60건 중 60건 통과이다.** 트랙 B 30건의 규칙 준수 검사도 30건 모두
통과하였다. 즉 60건 모두 구문적으로 유효하고, 요구된 작성 규약을 지켰으며, 지정된 API 를
호출한다. 코드 수준 지표만으로는 60건 사이에 어떠한 변별도 발생하지 않는다.

**동일한 60건을 물리 시뮬레이터에서 실행한 결과 통과는 0건이다.** 실패 양상은 표 2와 같이
네 유형으로 구분된다.

**표 2. 실패 유형 분포 (60건, 통과 0건)**

| 가속기 | n | 통과 | 저평면 충돌 | 가시 충돌 | 정지 | 실행 오류 |
|---|---|---|---|---|---|---|
| GPU | 30 | 0 | 6 | 17 | 7 | 0 |
| NPU | 30 | 0 | 4 | 18 | 6 | 2 |
| 계 | 60 | 0 | 10 | 35 | 13 | 2 |

각 유형의 정의는 다음과 같다. **저평면 충돌**은 센서 평면 아래 상자와 접촉한 경우로,
센서 모델에 대한 잘못된 가정에서 비롯된다. **가시 충돌**은 센서에 검출되는 물체와 접촉한
경우로, 회피 제어 자체의 실패이다. **정지**는 충돌 없이 목표에 도달하지 못한 경우이다.
**실행 오류**는 컨트롤러가 예외를 발생시켜 하네스가 판정에 이르지 못한 경우로, 2건 모두
`UnboundLocalError` 였다. 실행 오류는 누락이 아니라 실패 유형으로 집계하였다 — 제외하면
실행 중 중단된 코드가 평가에서 유리해지기 때문이다.

실행 오류 2건은 정적 검증과 물리적 실행의 간극이 가장 단순하게 드러난 사례이다. 해당 코드는
구문 분석을 통과하고 작성 규약을 지켰으나, 특정 분기에서 반환 변수가 할당되지 않아 실행 중
중단되었다. 정적 검증이 이를 감지하지 못한 것은 검증의 결함이 아니라 **코드 수준 검증의
정의상 범위 밖**이기 때문이다.

한편 두 가속기 환경의 실패 분포는 사실상 겹친다. 통과 건수는 양쪽 모두 0이고, 유형별 비율도
유사하다. 이는 **본 평가에서 관측되는 차이가 서빙 백엔드가 아니라 모델과 과제에서 비롯됨**을
지지한다.

## 3. 환경 명세 활용 실패

2.4절의 결과는 간극의 존재를 보이지만 원인을 말하지 않는다. 본 절은 **제공된 명세가 생성
코드의 작성 과정에서 실제로 참조되었는지**를 측정한다.

### 3.1 측정 방법

측정 대상은 상자 표 열람이 허용된 트랙 A 의 전체 응답 **119건**이다(1회차 30건, 4장의 반복
검증 과정에서 생성된 89건). 각 응답의 코드, 주석, 산문, **모델의 추론 트레이스 전체**를
대상으로, 2.2절의 두 값을 어디까지 연결했는지 4단계로 분류하였다.

| 단계 | 정의 |
|---|---|
| L0 | 상자 높이와 센서 평면 중 어느 쪽도 언급하지 않음 |
| L1 | 둘 중 한쪽만 언급 |
| L2 | 둘 다 언급하나 서로 관련짓지 않음 |
| L3 | 두 값을 교차 참조하여 "검출되지 않는다"는 귀결을 명시 |

분류는 정규식 기반 자동 탐지 후 **119건 전수를 수동 확인**하였다. 자동 탐지 결과를 그대로
쓰지 않은 이유는 3.3절에 기술한다.

### 3.2 결과

**119건 중 상자 높이와 센서를 올바르게 연결한(L3) 응답은 0건이다**(표 3). 두 값을 함께
언급한 응답은 1건(L2)이었는데, 그 응답은 결론이 반대였다. 트랙 A 는 상자 표 열람이 명시적으로
허용된 조건이다.

**표 3. 환경 명세 활용 단계 (트랙 A 응답 119건)**

| 척도 | L0 | L1 | L2 | L3 |
|---|---|---|---|---|
| 자동 탐지(1차) | 3 | 109 | 7 | 0 |
| 보수적 정규식 | 118 | 1 | 0 | 0 |
| **전수 수동 확인(최종)** | **118** | **0** | **1** | **0** |

추론 트레이스의 분량도 이 결과와 무관하였다. 응답당 추론 트레이스가 23,000자 규모인 모델
역시 전부 L0 이었다. **명세를 연결하지 못한 것은 사고 과정의 분량 부족이 아니다.**

**유일한 L2 응답은 명세를 읽고도 물리를 거꾸로 적용했다.** 30회차 반복의 마지막 회차에서
모델은 `"The box at (0.2, -9.6) width 1.2 depth 0.8 height 0.2. … The ray fan forward 180 degrees
may see that box at some bearing"` 라고 추론한다. 높이 0.2 m 를 정확히 읽었으나, 0.35 m 평면을
훑는 센서가 그 상자를 **볼 수 있다**고 판단한 것이다. 정보의 부재가 아니라 정보와 물리의
연결이 실패한 사례를 이보다 직접 보여주는 것은 없다.

L0 응답 중 상자 높이에 가장 근접한 것은 `"Check boxes heights:"` 라고 기술한 직후 다음
문장에서 `"The highest y of boxes? Box 06 at y=13.4 depth 1.0"` 으로 서술을 이어간다. 높이를
지칭하는 낱말을 사용하였으나 곧바로 평면상의 y 좌표로 대상을 바꾼 것으로, 본 환경에서 명세
활용 실패가 발생하는 양상을 단적으로 보여준다.

### 3.3 분류의 타당성

자동 탐지 1차에서 L0 이 아닌 것으로 분류된 8건은 **전수 수동 확인 결과 모두 오탐**이었다.
오탐의 원인은 (i) 제어 이득 상수 `SAFETY_STOP = 0.25`, `v = 0.25` 가 상자 높이 값으로 일치,
(ii) 상자 좌표 `(−2.35, −2.57)` 의 소수부가 센서 평면 값 `0.35` 와 일치, (iii) 기반 파일의
센서 서명 `raycast_scan(..., z=0.35, ...)` 을 그대로 재기술한 복창, (iv) `height`, `low`,
`tall` 을 평면상의 y 좌표를 지칭하는 의미로 사용한 경우였다. 특히 (iv)의 한 응답은 높이
0.18 m 의 상자를 `"tall box"` 로 기술한다.

분류기가 실제 교차 참조를 탐지하는지 확인하기 위해 **양성 대조**를 수행하였다. 본 환경을
통과한 참조 구현을 동일 분류기에 입력한 결과 **L3 으로 분류**되었으며, 판정 근거로 추출된
문장은 `"…04 (0.25) all stand below the z = 0.35 m scan plane, so the ray fan can never…"`
이다. 즉 표 3의 결과는 분류기의 탐지 실패가 아니다.

## 4. 반복 검증 루프의 한계

3장의 결과는 실패 원인이 정보 부족이 아님을 보인다. 그렇다면 **실행 결과를 되돌려주는 반복
검증이 이를 교정할 수 있는지**가 다음 질문이 된다.

### 4.1 프로토콜

1회차는 프롬프트와 기반 파일만 보고 작성한다. 실패하면 **동일한 대화를 이어** 해당 실행의
판정 결과를 제공하고 재제출을 받는다. 모델이 이전 회차의 자신의 추론을 유지한 상태에서
수정하도록 하기 위함이다. 되돌려주는 내용은 판정 결과에 한정하며 환경의 배치는 제공하지
않는다. 트랙 B 에 대해서는 충돌 대상 프림 이름과 충돌 시각을 제거한다 — 이 두 값은 출발
자세와 평균 속도를 이용해 접촉 지점을 역산할 수 있어 트랙 B 의 규칙을 무력화한다.

정적 검증 실격과 실행 오류도 각각 한 회차로 집계하며, 전자에는 수정 구역 외부의 어느 행이
어떻게 달라졌는지를 함께 제공한다. 실험 대상은 gpt-oss-120b 이며, 트랙 A 5표본과 트랙 B
1표본에 대해 양쪽 가속기 환경에서 회차 상한 8로 수행하여 **12개 실행 93회차**를 얻었다.

### 4.2 수렴 실패

**12개 실행 93회차에서 통과는 1건이다.** 분류 규칙에 의존하지 않는 형태로 기술하면, 두
판정 조건(충돌 발생, 목표 미도달)의 위반 개수를 회차에 따라 추적할 때 **두 조건을 모두
해소한 실행은 1/12 이고, 8회차 동안 어느 조건도 해소하지 못한 실행은 6/12 이다.**

회차 상한이 부족한 것이 원인인지 확인하기 위해 한 표본에 대해 **상한을 30회차로 확장**하여
반복하였다. 최소 거리는 13.94 m 에 머물렀고(허용치 0.75 m), 충돌 횟수는 30회차 내내 0과
360 사이를 반복하였다. **22회차를 추가로 제공하여도 동일한 영역을 벗어나지 못하였다.**

### 4.3 오라클 회피

수렴 실패의 양상은 충돌 횟수와 **저평면 장애물까지의 최근접 거리**를 함께 관찰할 때 드러난다
(그림 3). 후자는 실행 전체에서 로봇이 센서 평면 아래 상자의 밑면에 가장 가까이 접근한 거리로,
해당 실행이 저평면 장애물에 의해 실제로 시험받았는지를 나타낸다.

대표적인 두 실행의 회차별 추이는 다음과 같다.

| 실행 | 충돌 횟수 추이 | 저평면 최근접 거리 추이 |
|---|---|---|
| 정지 수렴 사례 | 360 → 360 → 360 → 360 → 205 → 117 → 27 → **0** | 0.14 → … → **8.46 m** |
| 통과 사례 | 360 → 360 → 0 → 0 → **0** | 0.10 → 0.09 → 0.50 → 0.70 → **0.70 m** |

전자는 충돌 횟수를 단조 감소시켜 8회차에 0을 달성하였으나, 최종 거리는 31.9 m 로 출발
지점(32.0 m)과 사실상 동일하다. **충돌 조건을 해소하는 과정이 저평면 장애물이 존재하는
영역에서 이탈하는 과정과 동일하게 진행된 것이다.**

12개 실행 중 **6건**에서 회차에 따라 충돌 횟수가 감소하면서 저평면 최근접 거리가 증가하는
추세가 관측되었다. 이 중 **4건**은 최종 최근접 거리가 센서의 `max_range` 인 6.0 m 를 넘었다.
즉 해당 상자가 센서 범위 밖에 놓일 만큼 영역을 이탈하였다.

반면 **통과한 유일한 실행은 저평면 장애물 부근을 벗어나지 않았다.** 최근접 거리가 0.10 m
에서 0.70 m 로 증가하였으나, 이는 영역 이탈이 아니라 통과에 필요한 여유를 확보한 것이다.
이 실행은 충돌, 위치, 자세 조건을 한 회차에 하나씩 순차적으로 해소하여 5회차에 통과하였다.

### 4.4 피드백 상세도의 영향

되돌려주는 정보의 양이 수렴에 영향을 주는지 확인하기 위해 **단일 변수 절제 실험**을
수행하였다. 동일한 1회차 결과물에서 분기하여 피드백 필드 집합만 달리하였으며, 1회차 응답의
해시가 두 조건에서 일치함을 확인하였다.

**표 4. 피드백 상세도 절제 (5표본 × 2조건 × 8회차 = 80회차)**

| 조건 | 제공 정보 | 길이 | 실행 | 회차 | 통과 |
|---|---|---|---|---|---|

## 5. 명세 연결을 유도하는 두 가지 시도

3장과 4장의 결과는 실패가 정보 부족과 피드백 부족 어느 쪽에서도 비롯되지 않음을 보인다.
본 절은 명세와 물리를 연결하도록 유도하는 두 가지 방법을 시험한다.

**첫째, 외부 검사 코드의 작성을 지시하였다.** 트랙 A 프롬프트에 *"컨트롤러를 작성하기 전에
주어진 장애물 명세와 센서 명세를 서로 대조하는 검사 코드를 먼저 작성하고 그 결과를 설계의
근거로 삼으라"* 는 한 문장만 추가하고 나머지는 동일하게 유지하였다. 추가 문장이 정답을
누설하지 않는지 사전 감사하였다 — 상자 높이 값, 센서 평면 값, "검출되지 않는다" 류의 귀결,
특정 상자 번호를 포함하지 않는다.

결과는 통과 0/5 이며, 3장의 단계 분포 역시 변화가 없었다. 5건 모두 추론 트레이스에서 지시를
정확히 재진술하였으나 **4건이 출력 형식 제약을 이유로 검사 작성을 생략**하였다. 검사를 작성한
1건은 센서의 빔 개수와 최대 거리가 문서와 일치하는지를 확인하는 코드로, **장애물 명세를
참조하지 않는다.** 따라서 본 결과는 "외화 지시만으로는 부족하며 **무엇과 무엇을 대조할지까지
지정**되어야 한다" 로 해석된다. 다만 본 실험 조건에서 모델은 코드를 실행할 수 없으므로,
작성과 실행을 모두 포함하는 조건은 후속 과제로 남는다.

**둘째, 명세 일관성 정적 검사를 구현하여 소급 적용하였다.** 기반 파일의 상자 표에서 높이를,
하네스에서 센서 평면 기본값을 각각 파싱하여 평면 아래 상자 집합을 구성하고, 제출 코드가 해당
상자를 지도 기반 장애물로 취급하거나 센서 평면을 낮추었는지 검사한다. 두 조건 모두 해당하지
않으면 시뮬레이터 실행 **이전에** 경고한다.

채점이 완료된 161건에 소급 적용한 결과, **실제 저평면 충돌 35건을 모두 경고하였으나
(재현율 100%) 경고 146건 중 실제 충돌은 35건이었다(정밀도 24%).** 전체의 91%에 경고가
발생하며 **유일한 통과 제출에도 경고가 발생한다.** 본 검사는 정답을 알고 작성한 것이므로
일반적 탐지기가 아니다. 이 결과가 보이는 것은 **본 실패가 기계적으로 검증 가능한 종류였다**는
사실이며, 범용 도구를 제시하는 것은 아니다.

## 6. 결론 (초안)

본 논문은 LLM 이 생성한 로봇 제어 코드에서 정적 코드 검증과 물리적 실행 결과 사이의 간극을
실측하고 그 원인을 분석하였다. 공개 가중치 모델 3종으로 수집한 60건은 **정적 검증을 60건 모두
통과하였으나 물리적 실행에서는 통과가 0건**이었다.

간극의 원인을 확인하기 위해 환경 명세의 활용 여부를 측정한 결과, 상자 표 열람이 허용된
트랙 A 의 **응답 119건 중 상자 높이와 센서 평면을 교차 참조한 응답은 0건**이었다. 두 값은
모두 모델에 제공된 파일 안에 평문으로 기술되어 있었다. **실패는 정보의 부재가 아니라 제공된
명세가 제어 코드로 연결되지 않은 데서 비롯된다.**

실행 결과를 반복적으로 되돌려주는 검증 루프는 이를 교정하지 못하였다. 12개 실행 93회차에서
통과는 1건이었고, 회차 상한을 30으로 확장하여도 동일하였다. 더 나아가 루프가 진행되는 동안
**충돌 조건이 해소되는 과정이 저평면 장애물 영역에서 이탈하는 과정과 동일하게 나타났으며**,
통과한 유일한 실행만이 해당 영역에 머물렀다. 되돌려주는 정보의 양을 늘린 절제 실험에서도
통과는 발생하지 않았다.

이상의 결과는 코드 수준 평가가 생성 코드의 문법적·기능적 유효성을 측정하는 데에는 유효하나,
**환경 명세가 물리적 제어로 연결되었는지는 측정하지 못함**을 보인다. 또한 실행 결과만을
되돌려주는 반복 검증은 모델이 진단 가능한 판정 조건을 우선 해소하도록 유도하며, 그 과정이
과제의 본질적 난점을 회피하는 방향으로 진행될 수 있음을 실험적으로 확인하였다.

**한계.** 본 연구는 단일 주행 환경에서 수행되었으며 조건당 표본 수는 5이다. 반복 검증은
gpt-oss-120b 한 모델에 대해서만 수행하였다. 유일한 통과 사례는 허용치 0.75 m 에 대해 0.70 m
로 여유가 0.045 m 이며, 8회 반복 실행에서 동일하게 통과하였다. 생성은 비트 단위로 재현되지
않는다 — 한 서빙 스택은 요청 단위 난수 시드를 적용하지 않으며, 다른 스택은 시드를 적용하나
temperature 0.7 에서 동일 시드 5회 중 1회가 상이하였다.

## 집필 시 주의 — 쓰지 말 것

본 초안에서 의도적으로 배제한 표현이다. 모두 과거 판본에 있었으나 실측으로 철회되었다.

1. **"풍부한 피드백이 더 나쁘다"** — 교란된 비교(두 트랙은 피드백 상세도와 좌표 열람 허용
   여부가 동시에 다름)에서 나온 진술이다. 단일 변수 절제에서는 상세 조건이 근소하게 우세하다.
2. **"두 서빙 스택 모두 temperature 0 에서 완전히 결정적"** — 한쪽 데이터가 생성 토큰의 6%
   만 비교한 것이어서 철회하였다. 현재 근거가 있는 것은 한쪽 스택뿐이다.
3. **"함정(trap)"** — 정보를 모두 공개하였으므로 은닉이 아니다. **저평면 장애물**로 쓴다.
4. **비율 표현** — 표본 5에서 1건을 "20%" 로 쓰지 않는다. "5회 중 1회" 로 적는다.
5. **가속기 우열** — 카드 수가 다르므로(4장 대 1장) 장당 성능을 주장하지 않는다.

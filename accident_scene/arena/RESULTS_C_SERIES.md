# C 계열 실험 결과 (2026-11-15 ~ 11-23, 서버 fractal)

역할을 나눈 LLM 에이전트(코더·검토·분석)가 Nova Carter 경유점 제어기를 고쳐, 무작위로 놓인 이동 장애물
(`ARENA_MOVERS=v1r`)을 피해 목표에 도달하게 만드는 실험이다. 역할별 모델만 바꿔 가며 같은 과제를 돌렸다.

## 과제와 통과 기준

- 출발 코드: A-4 경유점 추종(속도 5배, 센서 미사용). `results/turns/prompt_c2_turn0/start_block.py`
- 기반 파일 `base_carter_run_c2.py`, 과제 프롬프트 `PROMPT_C2.md`, 분석 프롬프트 `PROMPT_C1_ANALYST.md`, 검토 프롬프트 `PROMPT_C1_REVIEWER.md`
- 한 턴 = 코더 → 검토 → 정적 검사 → 새 무작위 배치로 Isaac 실행(최대 10회) → 분석. 분석의 진단이 다음 턴 코더의 입력
- **통과 = 한 턴에서 10회 모두 통과하고 시뮬 시간 합계가 600 s 이하** (실행당 평균 60 s)
- 턴 예산 600 s 를 실행들이 나눠 쓰고(실행별 한도 = 남은 예산), 3회 실패하면 그 턴의 실행을 끝낸다. 정지 60 s·진행 부족 90 s 면 실행 중단

- 성공한 계열은 분석이 Claude 인 둘(C-3, C-4)과 Gemma 4 31B 에 사실 자료·시작 코드 고르기를 더한 C-7c 다. 코더 모델은 성패를 가르지 않았다. C-7c 는 한 번 돌린 결과이고 여유가 8 s 였으며, 같은 모델의 C-7·C-7b 는 실패했다. 성공 코드를 새 배치로 다시 확인하지 않았다.
- 공개 모델 분석의 공통 양상: 직전 턴의 실패 하나에 반응해 값을 오가거나 접근법을 갈아탐, 이미 실패한 처방을 다시 꺼냄, 가장 좋았던 코드를 기준점으로 지키지 못함, 맞는 방식(물체 추적과 예측)을 후보에 올리고도 "구현이 복잡하다"며 고르지 않음.
- C-7 과 C-7b 에서 성적이 오른 전환점은 둘 다 코더가 지시 범위를 넘어 추적·예측 구조를 넣은 턴이었다(C-7 1턴, C-7b 20턴). 분석은 그 구조가 생긴 뒤에야 좁은 조정을 했다.
- 한계: 계열마다 한 번씩만 돌렸다(반복 없음). 배치가 매번 무작위라 편차가 크고, 같은 모델인 C-7 과 C-7b 의 흐름이 크게 달랐다. 공개 모델끼리의 순위는 이 자료로 말하기 어렵다.
- 모델 호출: gpt-oss-120b, Qwen3.6-27B(BF16), Gemma 4 31B(BF16, KV 캐시만 fp8)는 vLLM 0.32.0(`fractal_setup/serve_*.sh`, 문맥 131072), Claude 는 `claude -p --tools "" --effort high`(`agent_loop.claude_post`). Qwen 은 추론이 기본 켜짐, Gemma 는 `enable_thinking` 을 요청에 넣음.
- EXAONE 4.5 33B 는 vLLM 에서 `TRITON_ATTN` + KV 캐시 fp8 로 올렸다(`fractal_setup/serve_exaone45-33b_gpu.sh`).

## 시작 코드 고르기(되돌리기)를 넣은 세 계열 (C-7c, C-8b, C-5b)

분석의 답에 `last_direction_ok`(직전 지시가 옳았는지)와 `base_turn`(다음 코더가 어느 턴의 코드에서 시작할지)을 넣었다.
`base_turn` 이 이번 턴이 아니면 그 턴의 코드를 분석에 보여 주고 지시를 다시 쓰게 한다(2단계). 자동 진행이 그 턴의 코더 작성
코드와 새 지시를 다음 코더에게 넘긴다.

- **바닥은 생겼다.** 되돌리기가 없던 C-8 은 17턴 이후 코드가 1,055 → 1,759줄로 불며 0/3 이 이어졌다. 같은 모델의 C-8b 는 무너진 턴 뒤에 좋았던 코드로 돌아가 30턴까지 6~8회 통과 수준과 450~620줄을 지켰다. C-5 (2,993줄, 최고 7/10)와 C-5b (527~682줄, 9/10·9/9 여섯 번)도 같은 차이다.
- **천장은 오르지 않았다.** C-8b 는 통과 실행 평균이 69 s 아래로 내려간 턴이 없어 10회를 다 돌린 적이 없다. C-5b 는 빠르지만 열 번에 한 번 부딪히는 코드(1·3·5턴, 평균 62~63 s)와 부딪히지 않지만 느린 코드(8·24·28턴, 평균 65~66 s) 사이를 오갔다.
- **모델마다 되돌리는 시점이 달랐다.** gpt-oss-120b 는 나빠진 다음 턴에 바로 되돌렸고(30턴 중 20번이 이번 턴이 아닌 코드 선택), EXAONE 은 초반에는 0/3 처럼 크게 무너진 뒤에야 되돌렸다. Gemma 는 3턴 만에 끝나 되돌릴 일이 없었다.
- **gpt-oss-120b 는 충돌 없는 9/9 를 세 번 모두 "느려졌으니 직전 지시가 틀렸다"로 판정했다**(8·24·28턴). 그 코드에서 시간만 줄이는 대신 다른 처방을 시도했고, 9·16턴에는 같은 처방(정지·우회 상태 기계 제거)을 되풀이해 4/7, 0/3 이 됐다. 29턴 분석은 "28턴 코드가 9/9"라고 쓰고도 3/6 이었던 29턴을 시작 코드로 골랐다.
- EXAONE 은 JSON 괄호가 어긋난 답이 잦아, 어디서 틀렸는지 알려 주고 다시 받는 재시도를 넣었다. `base_turn` 을 빠뜨리는 일도 잦았다(빠지면 다시 요청).

## 실험 도중 바꾼 것 (계열 비교 시 감안)

- C-2 35턴부터 분석 프롬프트에 "진단 전에 먼저 답할 것"(가정 점검, 접근법 계열, 구조가 다른 후보 2~3개) 추가. 이전 판은 `PROMPT_C1_ANALYST_until_turn34.md`
- C-3 2턴 뒤 과제 프롬프트에 통과 기준(턴 예산 600 s, 실행당 평균 60 s) 명시. 이전 판은 `PROMPT_C2_until_c3turn2.md`
- C-3 진행 중 분석 입력에 코드의 DBG 출력(실행별 처음 10줄 + 마지막 50줄, 줄당 300자)과 잘린 양 통계 추가
- C-5 부터 vLLM 분석 모델은 입력이 문맥 한도를 넘으면 DBG 줄 수를 줄이는 장치 추가(C-5~C-7b 에서 한 번도 작동하지 않음)
- C-7b, C-8, C-7c, C-8b, C-5b 에만(`c1_cycle.FACT_SERIES`): 분석 입력에 (1) 이번 턴 실행 집계 - 10개 중 몇 개를 실행했고 왜 나머지를 못 했는지, 통과 실행의 평균 시간과 필요한 60 s, 통과 기준 충족 여부, (2) 검토 담당이 진단에 대해 적은 의문을 넣는다. C-7 의 14·25턴에 분석이 7/7, 8/8 을 완료로 읽은 것이 계기다.
- C-7b 3턴: 하네스의 근거 검사가 "stall_abort." 의 마침표를 숫자로 읽어 죽었다. 고친 뒤 3턴의 분석만 같은 입력으로 다시 받았다(원래 답은 `*_raw_crashed_BAD.json`).
- C-7c, C-8b, C-5b 에만(`REVERT_SERIES`): 분석 답에 `last_direction_ok`, `base_turn` 추가, 되돌릴 때 2단계(그 턴 코드를 보고 지시 재작성), 이전 턴 요약표에 "시작한 코드"·"통과 실행 평균 시간" 열, JSON 이 깨진 답에는 틀린 위치를 알려 주는 재시도, 코더·검토에게 "시작 코드에 대해" 안내. 다른 계열의 입력은 그대로다.
- C-8 부터 턴 실행기에 실제 시간 한도(멈춘 Isaac 실행 대비)를 넣었고, 분석의 시도별 원문을 `*_raw_try<n>.json` 으로 남긴다.

## 하네스에 남은 틈 (미적용)

- 코더의 답 형식(바꿀 최상위 정의만 냄)으로는 정의를 지울 수 없다. 분석이 "제거하라"고 해도 코드가 남는다.
- 목표 근처에서 조금씩 움직이며 끝나지 않는 실행을 끊는 규칙이 없어, 한 실행이 턴 예산 600 s 를 다 쓸 수 있다(C-7b 17턴).
- 분석이 후보를 하나만 내거나 `failure_mode` 에 정해지지 않은 값을 적어도 걸러지지 않는다.
- 이전 턴 요약표에 충돌 상대와 위치가 없어, 같은 지점의 반복 충돌을 턴을 넘어 알아보기 어렵다.
- 되돌리기 2단계의 답에서 `chosen` 이 양식 문구 그대로이거나 `direction` 이 목록으로 오는 경우가 있다(걸러지지 않음).
- 분석이 "충돌 없이 전부 통과했지만 느린" 턴을 실패로 보고 버리는 것을 막는 장치가 없다(C-5b 8·24·28턴).

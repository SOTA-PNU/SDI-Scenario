# LLM 로봇 제어 코드 생성의 물리 시뮬레이션과 코딩 에이전트 작업 절차 분석

(An Analysis of LLM Robot-Control Code Generation in Physics Simulation and of a Coding Agent's Work Procedure)

**Abstract :** 대규모 언어 모델(LLM)이 생성한 로봇 제어 코드는 구문이나 규약 같은 코드 수준의 검사를 통과하더라도, 센서 특성과 접촉이 작용하는 물리 환경에서는 의도와 다르게 동작할 수 있다. 특히 공개 가중치 모델을 GPU나 NPU에서 직접 서빙하는 임베디드·로봇 현장에서는 이러한 코드를 어떻게 판정하고 개선할지가 중요하다. 본 연구에서는 Isaac Sim 창고 환경에서 Nova Carter 로봇의 주행 제어 함수를 작성하는 과제를 구성하고, 거리 센서의 기본 스캔 평면보다 낮은 상자 4개를 배치하여 생성 코드를 정적 검증과 물리 실행으로 판정하였다. 상자 높이와 스캔 높이는 모두 입력에 주어진다. 그 결과 GPU와 NPU에서 서빙한 공개 모델 3종의 1회차 코드 60건은 정적 검증을 모두 통과하였으나 물리 실행에서는 한 건도 통과하지 못하였고, 상자 표를 쓸 수 있는 조건의 1회차·재제출 응답 90건 중 상자 높이와 스캔 높이를 연결한 응답은 없었다. 반면 같은 입력을 받은 코딩 에이전트 Claude Code는 1회 실행에서 첫 회차에 통과하였으며, 그 작업 절차에는 낮은 상자에 대한 이른 판단과 높이를 반영한 자체 시뮬레이터 시험이 포함되어 있었다. 이 절차의 요소를 NPU에서 서빙한 gpt-oss-120b에 단계적으로 이식한 결과 통과는 11실행 중 1회(충돌 피드백 경유)에 그쳤다. 작업 순서를 지시하고 예산을 늘리자 설계 메모와 잦은 도구 호출 같은 절차의 일부 형식은 옮겨졌으나, 시뮬레이터는 높이를 버린 2D였고 시험 묶음은 만들어지지 않았다. 이는 서빙 모델로 제어 코드를 생성하는 현장에서 물리 실행 판정과 함께, 모델이 명세를 담은 검증 환경을 갖추게 하는 방법이 필요함을 시사한다.

**Keywords :** 대규모 언어 모델, 로봇 제어 코드 생성, 물리 시뮬레이션, 코딩 에이전트, 신경망 처리 장치(NPU)

## Ⅰ. 서 론

최근 LLM으로 자연어 지시에서 로봇 제어 코드를 생성하는 연구가 활발하다[1]. 생성 코드는 흔히 코드 수준의 검사로 평가되지만, 제어 코드의 성패는 센서 특성과 접촉이 작용하는 물리 환경에서 실행해 보아야 드러나는 경우가 많아 Isaac Sim[2] 같은 물리 시뮬레이터에서의 판정이 요구된다.

데이터를 외부로 보내기 어려운 임베디드·로봇 현장에서는 공개 가중치 모델을 GPU(vLLM[3])나 NPU(RNGD[4])에서 직접 서빙하기도 한다. 한편 코딩 에이전트는 숙고, 파일 작성과 실행, 자체 시험을 거쳐 결과를 제출한다. 같은 과제를 에이전트만 1회차에 통과한다면, 어떤 절차 요소가 차이를 만들고 그 요소를 서빙 모델에 옮길 수 있는지가 질문이 된다.

본 연구에서는 낮은 장애물 판단에 필요한 정보를 모두 공개한 주행 과제에서 서빙 모델과 에이전트의 제어 코드를 물리 시뮬레이션으로 판정하고, 에이전트의 작업 절차를 공개 모델에 이식하여 옮겨지는 요소와 아닌 요소를 분석하였다.

## Ⅱ. 본 론

### 1. 실험 구성

과제는 Isaac Sim 창고 장면에서 차동 구동 로봇 Nova Carter를 출발점에서 목표점까지 주행시키는 것이다(그림 1). 모델은 기반 파일의 수정 구역에 60 Hz로 호출되는 제어 함수 controller(t, pose, env)를 작성하며, 제어기가 얻는 감각은 로봇의 참값 자세와 가상 2D 거리 센서(env.raycast_scan())뿐이다. 이 센서는 기본값으로 높이 0.35 m의 수평면에서 전방 180°에 광선 61개를 쏘며 측정 높이를 바꿀 수 있고, 실제 라이다·카메라 데이터는 쓰지 않았다. 120 s 안에 목표에서 0.75 m, 0.26 rad 이내에 멈추고 상자·지게차·선반과 접촉하지 않으면 통과이다.

**그림 1. 평가 과제 상면도(주황: 저평면 장애물)**
**Fig. 1. Top view of the task (orange: low obstacles)**

창고에 놓인 상자 14개의 위치·크기·높이는 상자 표(MISSION)에 명시되어 있다. 이 중 4개는 높이가 0.18~0.25 m로 기본 스캔 평면보다 낮아(저평면 장애물), 각 상자의 1 m 밖에서 기본 높이의 광선을 쏘면 높이 1.0 m 상자 10개는 모두 검출되지만 저평면 장애물은 하나도 검출되지 않는다. 상자 높이와 스캔 높이가 모두 입력에 있으므로 숨겨진 정보가 아니며, 저평면 장애물을 알고 피하려면 상자 표를 지도로 쓰거나 스캔 높이를 낮춰야 한다. 상자 표 사용을 허용한 조건(트랙 A)을 주 실험으로, 상자 표와 좌표 하드코딩을 금지한 조건(트랙 B)을 보조로 두었다.

생성 코드는 구문, 수정 구역 밖 코드의 동일성, 트랙 규칙, 함수 정의를 확인하는 정적 검증을 거쳐 물리 실행으로 판정하며(수정 구역만 낸 응답은 기반 파일에 끼워 검사), 실패하면 같은 대화에 판정 결과를 덧붙여 재제출을 받는 회차 루프를 최대 8회차까지 반복하였다. 공개 모델 3종(gpt-oss-120b, Qwen3-32B-FP8, EXAONE-4.0-32B-FP8)은 표 1의 GPU와 NPU에서 같은 모델명으로 서빙하였고, 입력은 과제 설명과 기반 파일을 담은 메시지 하나이다. 1회차는 세 모델 모두 실행하였으나, 통과율에 모델 간 차이가 없어 회차 루프와 이식 실험은 gpt-oss-120b로만 수행하였다. 코딩 에이전트에는 트랙 A의 같은 입력을 주어 웹 도구·MCP를 끈 격리 환경에서 1회 실행하였으며(제출 전에 끊긴 시작 2회 제외), 예산이 달라 모델 비교가 아닌 절차 관찰에 사용하였다.

### 2. 공개 모델의 물리 실행 결과

표 2는 공개 모델의 실행 결과이다. 1회차 코드 60건(모델·가속기당 트랙 A·B 각 5건)은 정적 검증을 모두 통과하였으나 물리 실행에서는 한 건도 통과하지 못하였다. 실패의 절반 이상은 저평면이 아닌 물체(대부분 경로 초반의 상자 00·01)와의 충돌이었다. GPU와 NPU 각 30건의 실패 분포(저평면 충돌 6건과 4건 등)와 루프 통과도 구별되지 않았다.

1회차·회차 루프·이식 조건의 저평면 충돌 42건 중 원문이 남은 41건의 제어기는 모두 상자 표나 좌표 없이 기본 높이의 스캔만 호출하여, 부딪힌 장애물을 알 수단이 없었다(정보가 있었다면 피했을지는 시험하지 않음). 원문이 남은 트랙 A 응답 90건(1회차와 상한 8 루프)에서도 상자 높이와 스캔 높이를 연결한 응답은 없었다. 회차 루프에서 gpt-oss-120b는 12실행 중 GPU의 1실행만 통과하였는데, 이 역시 충돌 피드백이 알려 준 상자 06의 좌표를 상자 표에서 옮겨 하드코딩한 결과였다. 이러한 결과는 정적 검증의 통과가 물리 환경에서의 동작을 보장하지 않으며, 입력에 주어진 명세도 코드에 반영되지 않을 수 있음을 보여준다.

### 3. 코딩 에이전트의 작업 절차

반면 같은 입력을 받은 Claude Code는 첫 회차에 목표에서 0.10 m 거리에 접촉 없이 도착하였다. 약 90분의 작업 기록을 단계로 나누면 표 3과 같으며, 20분의 첫 초안 머리 주석에 이미 "Four boxes are lower than the default z=0.35 scan plane, so they are known only from MISSION"이라는 판단이 있었다. 이후 높이를 반영한 자체 시뮬레이터로 108개 상황을 시험하고, 회귀 시험과 바이트 대조를 거쳐 제출하였다.

| 단계 | 에이전트 | T2P (3실행) |

### 4. 작업 절차의 이식

NPU에서 서빙한 gpt-oss-120b의 트랙 A 회차 루프 5실행(T0)에 에이전트의 절차 요소를 한 겹씩 더하였다. 정답에 해당하는 내용(상자 표를 지도로 쓰는 방법, 높이별 센서 모델)은 빼고, 추가 문구는 실행 전 누설을 점검하였다. T3은 reasoning_effort를 high로 높인 조건(5실행), T2는 여기에 Python 실행 도구와 안내를 더한 조건(3실행)이며, T2P는 에이전트의 작업 순서를 담은 11단계 지시문과 큰 도구 예산을 주고 시험 기록·최종 확인·제출 파일 중 하나라도 갱신되지 않은 회차의 답을 한 번 반려한, 지시와 예산이 함께 달라진 묶음 조건(3실행)이다.

그 결과 T3은 5회 중 1회(8회차) 통과하였고 T2와 T2P는 통과하지 못하였다. T3은 추론 토큰이 약 14배 늘었으나 높이와 스캔을 연결한 응답은 없었고(두 실행은 빈 응답으로 조기 종료), 통과한 실행도 충돌 피드백을 거쳐 상자 표 기반 지도에 도달하였다. T2에서는 도구가 8회만 쓰였다. T2P에서는 도구 호출이 394회로 약 50배 늘었고 설계 메모와 조립 스크립트 같은 형식은 나타났으나(표 3), 시뮬레이터를 만든 두 실행은 상자를 높이 없는 2D로 넣었고(한 실행의 주석: "For simplicity, ignore z") 저평면 장애물을 놓치는 충돌을 재현할 수 없었고 시험 묶음도 만들어지지 않았다. 이는 순서 지시만으로는 명세를 읽어 낸 판단과 이를 담은 검증 환경이 옮겨지지 않을 수 있음을 보여준다. 다만 표본이 작고, 에이전트의 판단이 시뮬레이터보다 먼저 있었으며 에이전트 표본이 1건이라 각 요소의 효과는 단정할 수 없다.

## Ⅲ. 결 론

본 연구에서는 LLM의 로봇 제어 코드를 물리 시뮬레이션으로 판정하는 환경에서 서빙 모델과 코딩 에이전트의 결과와 작업 절차를 분석하였다. 그 결과 정적 검증을 통과한 코드도 물리 실행에서 실패할 수 있었고, 공개 모델의 응답에는 입력에 주어진 상자 높이와 스캔 높이를 올바르게 연결한 경우가 없었다. 에이전트의 절차를 이식하자 일부 형식은 옮겨졌으나 명세를 담은 자기 검증 환경은 옮겨지지 않았다. 따라서 서빙 모델로 제어 코드를 만드는 임베디드·로봇 환경에서는 물리 실행 판정과 함께, 모델이 정답 누설 없이 명세를 반영한 검증 환경을 갖추게 할 방법을 고려할 필요가 있다. 본 연구는 단일 환경, 적은 표본, 이상화된 감각(잡음 없는 스캔, 참값 자세)에 기반하며, 스캔 함수가 PhysX가 먼저 보고한 면을 돌려주는 성질(점검 빔의 2.6%)도 그 밖의 충돌 일부에 영향을 주었을 수 있다. 향후 실제 라이다·카메라 데이터와 더 많은 표본으로 분석을 넓힐 것이다.

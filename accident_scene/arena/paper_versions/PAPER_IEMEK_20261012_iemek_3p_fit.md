# LLM 로봇 제어 코드 생성의 물리 시뮬레이션과 코딩 에이전트 작업 절차 분석

(An Analysis of LLM Robot-Control Code Generation in Physics Simulation and of a Coding Agent's Work Procedure)

**Abstract :** 대규모 언어 모델(LLM)이 생성한 로봇 제어 코드는 코드 수준의 검사를 통과하더라도 실제 물리 환경에서는 실패할 수 있다. 데이터를 외부로 보내기 어려운 임베디드 및 로봇 현장에서는 공개 가중치 모델을 직접 서빙해 이런 코드를 만들기도 하므로, 생성 코드를 어떻게 판정하고 개선할지가 중요하다. 본 연구는 Isaac Sim에서 로봇이 장애물을 피해 목표까지 주행하는 과제를 만들고, 거리 센서의 기본 스캔 높이보다 낮아 스캔에 보이지 않는 상자를 놓았다. 상자의 높이와 센서의 스캔 높이는 모두 입력에 주어지므로, 이 과제는 모델이 주어진 명세를 읽고 코드에 반영하는지 본다. 생성 코드는 구문과 규약을 확인하는 정적 검증을 거친 뒤 물리 시뮬레이션에서 실행하여 판정하였다. GPU와 NPU에서 서빙한 공개 모델 gpt-oss-120b가 첫 시도에 낸 코드는 정적 검증을 모두 통과하였으나 물리 실행에서 한 건도 통과하지 못하였고, 상자 높이와 스캔 높이를 올바르게 연결한 응답도 없었다. 반면 코딩 에이전트 Claude Code는 1회 실행에서 첫 시도에 통과하였다. 작업 기록을 단계로 나누어 보면, 에이전트는 작업 초기에 낮은 상자를 파악하고 높이를 반영한 자체 시뮬레이터로 검증하였다. 이 작업 절차를 공개 모델에 단계적으로 적용하자 설계 메모나 잦은 도구 호출 같은 형식은 나타났지만 명세를 반영한 자체 검증 환경은 만들어지지 않았고, 통과는 11회 실행 중 충돌 피드백을 거친 1회뿐이었다. 이는 서빙 모델로 제어 코드를 만들 때 물리 실행을 통한 판정과 함께, 모델이 명세를 담은 검증 환경을 스스로 갖추게 하는 방법이 필요함을 시사한다.

**Keywords :** 대규모 언어 모델, 로봇 제어 코드 생성, 물리 시뮬레이션, 코딩 에이전트, 신경망 처리 장치(NPU)

## Ⅰ. 서 론

최근 LLM으로 자연어 지시에서 로봇 제어 코드를 생성하는 연구가 활발하다[1]. 생성 코드는 흔히 코드 수준의 검사로 평가되지만, 제어 코드의 성패는 센서 특성과 접촉이 작용하는 물리 환경에서 실행해 보아야 드러나는 경우가 많다. 따라서 Isaac Sim[2] 같은 물리 시뮬레이터에서 실행하여 판정할 필요가 있다.

데이터를 외부로 보내기 어려운 임베디드 및 로봇 현장에서는 공개 가중치 모델을 vLLM[3] 기반 GPU 서버나 RNGD[4] NPU에서 직접 서빙하기도 한다. 한편 코딩 에이전트는 한 번에 코드를 내는 대신 추론과 설계, 파일 작성과 실행, 자체 테스트를 거쳐 제출한다. 같은 과제에서 에이전트는 성공하고 서빙 모델은 실패한다면, 작업 절차의 어떤 요소가 차이를 만들었고 이를 서빙 모델에 옮길 수 있는지가 질문이 된다.

본 연구에서는 낮은 장애물을 판단할 정보를 모두 입력에 담은 주행 과제를 만들고, 공개 모델 gpt-oss-120b와 코딩 에이전트의 제어 코드를 물리 시뮬레이션으로 판정하였다. 또한 에이전트의 작업 절차를 공개 모델에 단계적으로 적용하여 옮겨지는 요소와 그렇지 않은 요소를 분석하였다.

## Ⅱ. 본 론

### 1. 실험 구성

과제는 그림 1과 같이 Isaac Sim 4.5.0 창고 장면에서 차동 구동 로봇 Nova Carter를 목표까지 주행시키는 것이다. 모델에게는 실행 틀을 갖춘 기반 파일이 주어지고, 모델은 그중 수정이 허용된 수정 구역에 60 Hz로 호출되는 제어 함수 controller(t, pose, env)를 작성한다. 제어기가 얻는 감각 정보는 시뮬레이터가 주는 로봇의 정확한 위치와 방향, 그리고 가상 2D 거리 센서 env.raycast_scan()뿐이다. 이 센서는 기본값으로 높이 0.35 m의 수평면에서 전방 180°에 광선 61개를 쏘며, 높이는 인자로 바꿀 수 있다. 실제 라이다와 카메라 데이터는 쓰지 않았다. 120 s 안에 목표에서 0.75 m, 목표 방향에서 0.26 rad 이내로 멈추고 상자, 지게차, 선반에 닿지 않으면 통과이다.

창고에 놓인 상자 14개의 위치, 크기, 높이는 기반 파일의 MISSION 상자 표에 적혀 있다. 이 중 높이 0.18~0.25 m로 기본 스캔 평면보다 낮은 4개를 저평면 장애물이라 한다. 각 상자의 1 m 밖에서 기본 높이로 광선을 쏘면 높이 1.0 m 상자 10개는 모두 검출되지만 저평면 장애물은 하나도 검출되지 않는다. 그러나 상자 높이와 스캔 높이가 모두 입력에 있어 숨겨진 정보는 아니다. 저평면 장애물을 알고 피하려면 상자 표를 지도로 쓰거나 스캔 높이를 낮춰야 한다. 주 실험은 상자 표를 쓸 수 있는 표 허용 조건이고, 상자 표와 좌표 하드코딩을 금지한 표 금지 조건은 보조로 두었다.

생성 코드는 먼저 구문, 수정 구역 밖 코드의 동일성, 표 금지 규칙, 함수 정의를 확인하는 정적 검증을 거친 뒤 물리 시뮬레이션에서 실행하여 판정한다. 실패하면 같은 대화에 판정 결과를 덧붙여 다시 제출하게 하는 회차 루프를 최대 8회차까지 반복하였다. 공개 모델 gpt-oss-120b는 RTX PRO 6000 GPU 1장의 vLLM 0.29.0과 RNGD NPU 4장의 furiosa-llm 2026.3.0으로 서빙하였고, 두 가속기의 모델 가중치가 같은지는 확인하지 않았다. 입력은 과제 설명과 기반 파일을 담은 메시지 하나이다. 코딩 에이전트로는 claude-opus-5-5 기반의 Claude Code 2.1.291을 쓰고, 표 허용 조건과 같은 입력을 주어 웹 도구와 MCP를 끈 격리 환경에서 1회 실행하였으며, 제출 전에 끊긴 두 번의 시작은 제외하였다. 에이전트는 쓸 수 있는 도구와 계산 예산이 공개 모델과 달라 성능 비교가 아니라 작업 절차를 관찰하는 데 사용하였다.

### 2. gpt-oss-120b의 물리 실행 결과

표 1은 gpt-oss-120b의 가속기별 결과이며, 실패는 저평면 장애물에 부딪힌 저평면 충돌과 그 밖의 물체에만 부딪힌 그 밖의 충돌로 나누었다. 1회차 코드 20건은 정적 검증을 모두 통과하고 실행 오류도 없었으나, 물리 실행에서는 한 건도 통과하지 못하였다. 실패의 대부분인 15건은 경로 초반의 상자 00과 01에 부딪힌 경우였고, 저평면 충돌은 4건이었다. GPU와 NPU는 실패 분포와 회차 루프 통과에 뚜렷한 차이가 없었다.

주: 가속기마다 1회차는 표 허용 조건과 표 금지 조건 각 5건, 회차 루프는 표 허용 조건 5회와 표 금지 조건 1회 실행이다.

회차 루프와 4절의 조건까지 합친 저평면 충돌 36건 중 코드가 남아 있는 35건에서 제어기는 모두 상자 표나 좌표를 쓰지 않고 기본 높이의 스캔만 호출하여, 부딪힌 장애물을 알 수단이 없었다. 다만 그 정보가 있었다면 피했을지는 확인하지 않았다. 기록이 남은 표 허용 조건 응답 70건에서도 상자 높이와 스캔 높이를 연결한 응답은 없었다. 회차 루프에서 통과한 GPU의 한 실행도 충돌 피드백이 알려 준 상자 06의 좌표를 상자 표에서 옮겨 하드코딩한 결과였다.

### 3. 코딩 에이전트의 작업 절차

반면 같은 입력을 받은 Claude Code는 첫 회차에 목표에서 0.10 m 지점에 접촉 없이 도착하였다. 약 90분의 작업 기록을 보면, 20분째에 쓴 첫 초안의 머리 주석에 "Four boxes are lower than the default z=0.35 scan plane, so they are known only from MISSION", 곧 낮은 상자 4개는 스캔 평면 아래에 있어 상자 표로만 알 수 있다는 판단이 이미 적혀 있었다. 이후 에이전트는 상자와 스캔 높이를 반영한 자체 시뮬레이터에서 108개 시나리오 테스트를 모두 통과시키고, 실패 사례를 재현하는 회귀 테스트를 거친 뒤, 수정 구역 밖이 원본과 같은지 바이트 단위로 대조하고 제출하였다.

### 4. 작업 절차의 적용

NPU에서 서빙한 gpt-oss-120b의 표 허용 조건 회차 루프 5회 실행을 기준 조건으로 삼아 에이전트의 작업 절차 요소를 하나씩 더하였다. 상자 표를 지도로 쓰는 법이나 높이별 센서 모델 같은 정답은 주지 않았고, 추가 문구에 정답이 없는지도 실행 전에 점검하였다. 추론 강화 조건은 추론 강도를 정하는 인자 reasoning_effort를 high로 높여 5회 실행하였다. 도구 조건은 여기에 Python 실행 도구와 안내를 더해 3회 실행하였다. 절차 지시 조건은 에이전트의 작업 순서를 담은 11단계 지시문과 더 큰 도구 예산을 주고, 테스트 기록 등 필수 파일을 갱신하지 않은 회차의 답은 한 번 돌려보내며 3회 실행하였다. 이 조건은 지시와 예산이 함께 달라져 요소별 효과를 따로 볼 수 없다.

그 결과 추론 강화 조건은 5회 중 1회가 8회차에 통과하였고, 도구 조건과 절차 지시 조건은 한 번도 통과하지 못하였다. 추론 강화 조건에서는 추론 토큰이 기준 조건의 약 14배로 늘었으나 높이와 스캔을 연결한 응답은 없었고, 통과한 실행도 충돌 피드백을 거쳐 상자 표를 지도로 쓰게 되었다. 도구 조건에서는 도구가 8회만 쓰였으나 절차 지시 조건에서는 394회로 약 50배 늘었고, 세 실행 모두 설계 메모와 병합 스크립트를 만들었다. 그러나 상자 높이와 스캔 높이를 올바르게 연결한 응답은 없었고, 시뮬레이터를 만든 두 실행은 상자를 높이 없는 2D로 넣었으며, 한 실행은 주석에 "For simplicity, ignore z"라고 적었다. 이런 시뮬레이터로는 저평면 충돌을 재현할 수 없고, 시나리오 테스트와 실패 사례 재현도 이루어지지 않았다. 다만 표본이 작고, 에이전트의 판단은 시뮬레이터보다 앞섰으며, 에이전트 실행이 1회뿐이라 요소별 효과는 단정할 수 없다.

## Ⅲ. 결 론

본 연구는 LLM이 생성한 로봇 제어 코드를 물리 시뮬레이션으로 판정하고 코딩 에이전트의 작업 절차를 분석하였다. gpt-oss-120b가 첫 시도에 낸 코드 20건은 정적 검증을 모두 통과하고도 물리 실행에서 모두 실패하였고, 상자 높이와 스캔 높이를 올바르게 연결한 응답도 없었다. 에이전트의 작업 절차를 공개 모델에 적용하자 일부 형식은 옮겨졌으나 명세를 담은 검증 환경은 옮겨지지 않았다. 따라서 서빙 모델로 제어 코드를 만드는 임베디드 및 로봇 현장에서는 물리 실행을 통한 판정과 함께, 정답을 알려 주지 않고도 모델이 명세를 반영한 검증 환경을 갖추게 하는 방법이 필요해 보인다. 다만 본 연구는 하나의 환경과 하나의 공개 모델, 적은 표본, 이상화된 감각에 기반하며, 스캔 함수가 가장 가까운 면보다 먼 면의 거리를 돌려주는 경우가 빈 바닥에서 쏜 점검용 광선의 2.6%에서 나타나 그 밖의 충돌 일부에 영향을 주었을 수 있다. 향후 실제 라이다와 카메라 데이터를 쓰고 표본을 늘려 분석을 넓힐 계획이다.

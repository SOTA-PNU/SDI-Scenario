# LLM 로봇 제어 코드 생성의 물리 시뮬레이션과 코딩 에이전트 작업 절차 분석

(An Analysis of LLM Robot-Control Code Generation in Physics Simulation and of a Coding Agent's Work Procedure)

**Abstract :** 대규모 언어 모델(LLM)이 생성한 로봇 제어 코드는 코드 수준 검사를 통과해도 물리 환경에서 실패할 수 있다. 본 논문은 Nova Carter 로봇의 60 Hz 제어 함수를 작성하는 주행 과제와, 생성 코드를 정적 검증과 Isaac Sim 물리 실행으로 판정하는 평가 환경을 구축하였다. 상자 14개 중 4개는 거리 센서의 기본 스캔 평면(0.35 m)보다 낮으며, 상자 높이와 스캔 높이는 모두 입력에 주어진다. GPU와 NPU에서 서빙한 공개 가중치 모델 3종의 1회차 코드 60건은 정적 검증을 모두 통과하였으나 물리 실행 통과는 0건이었고, 판정을 되돌려주는 회차 루프에서도 gpt-oss-120b는 12개 실행 중 1개만 통과하였다. 상자 표 사용을 허용한 1회차·회차 루프 응답 90건 중 상자 높이와 스캔 평면을 연결한 응답은 없었다. 같은 입력을 받은 코딩 에이전트 Claude Code는 1회 실행에서 1회차에 통과하였다. 에이전트는 시험 전 첫 초안에서 이미 낮은 상자가 기본 스캔 평면 아래라 상자 표로만 알 수 있다고 판단했고, 이어 높이를 반영한 자작 시뮬레이터로 108개 상황을 시험하였다. 이 절차의 요소를 NPU 서빙 gpt-oss-120b에 이식하자 숙고 조건은 5회 중 1회 통과하였으나, 높이와 스캔을 연결하지 않고 충돌 피드백으로 도달한 것이었다. 숙고+도구 조건과 작업 순서 지시 조건은 각각 3회 중 0회였다. 작업 순서를 지시하고 도구 예산을 늘리자 도구 호출은 숙고+도구 조건의 약 50배가 되었으나, 시뮬레이터는 높이를 버린 2D였고 시험 묶음은 만들어지지 않았다. 절차의 일부 형식은 옮겨졌으나 명세를 담은 자기 검증 환경은 옮겨지지 않았다.

**Keywords :** 대규모 언어 모델, 로봇 제어 코드 생성, 물리 시뮬레이션, 코딩 에이전트, 신경망 처리 장치(NPU)

## Ⅰ. 서 론

LLM이 생성한 로봇 제어 코드[1]는 흔히 코드 수준 검사로 평가되지만, 그 성패는 센서 특성과 접촉이 작용하는 물리 환경에서 실행해야 드러나며 Isaac Sim[2] 같은 물리 시뮬레이터로 판정할 수 있다.

한편 숙고하고 파일을 만들어 실행하며 스스로 시험한 뒤 제출하는 코딩 에이전트만 같은 과제를 1회차에 통과한다면 절차의 어느 요소가 차이를 만드는지가 질문이 되며, 데이터를 외부로 보내지 않으려고 공개 가중치 모델을 GPU(vLLM[3])나 NPU(RNGD[4])에서 서빙하는 임베디드·로봇 현장에서는 서빙 모델에 그 절차를 옮길 수 있는가의 문제가 된다. 본 논문은 낮은 장애물 판단에 필요한 정보를 모두 공개한 주행 과제에서 GPU·NPU 서빙 공개 모델 3종의 코드를 물리 실행으로 판정하고, 에이전트의 작업 절차를 단계별로 공개 모델에 이식하여 옮겨진 요소와 그렇지 않은 요소를 보인다.

## Ⅱ. 본 론

### 1. 과제와 평가 환경

과제는 Isaac Sim 창고 장면에서 차동 구동 로봇 Nova Carter를 (−9.0 m, −10.8 m)에서 (8.0 m, 16.5 m)까지 주행시키는 것이다(그림 1). 모델은 기반 파일(base_carter_run.py)의 수정 구역에 60 Hz로 호출되는 controller(t, pose, env) → (v, w, done)을 작성한다. 제어기의 감각은 참값 자세와 env.raycast_scan()뿐이며, 후자는 기본값으로 높이 z = 0.35 m의 수평면에서 전방 180°에 광선 61개를 쏘는 잡음 없는 가상 거리 센서이다(z 변경 가능, 로봇의 라이다·카메라 데이터는 주지 않음). 120 s 안에 목표에서 0.75 m·yaw 0.26 rad 이내로 멈추고 상자·지게차·선반과 접촉하지 않으면 통과이다.

**그림 1. 평가 과제 상면도(주황: 저평면 장애물)**

상자 표(MISSION)는 상자 14개의 위치·크기·높이를 명시하며, 상자 04·05·06·13은 높이 0.18~0.25 m로 기본 스캔 평면보다 낮다(저평면 장애물). 각 상자의 1 m 밖에서 z = 0.35 m 광선을 쏘면 높이 1.0 m 상자 10개는 모두 검출되고 저평면 장애물 4개는 하나도 검출되지 않는다. 상자·스캔 높이가 입력에 평문으로 있으므로 은닉 정보가 아니며, 저평면 장애물을 알고 피하려면 상자 표를 지도로 쓰거나 스캔 높이를 낮춰야 한다. 주 실험은 상자 표 사용을 허용하는 트랙 A이고, 상자 표 참조와 좌표 하드코딩을 금지하는 트랙 B는 보조이다.

생성 코드는 정적 검증(구문, 수정 구역 밖 바이트 동일성, 트랙 B 규칙, controller() 정의)을 거쳐 Isaac Sim 4.5.0에서 물리 실행한다. 수정 구역만 낸 응답은 기반 파일에 끼워 넣어 검사하고, 실패하면 같은 대화에 판정 결과를 덧붙여 재제출을 받는다(회차 루프, 상한 8회차; 정적 실격·실행 오류도 한 회차). 공개 모델 3종(gpt-oss-120b, Qwen3-32B-FP8, EXAONE-4.0-32B-FP8)은 GPU(RTX PRO 6000 1장, vLLM 0.29.0)와 NPU(RNGD 4장, furiosa-llm 2026.3.0)에서 같은 모델명으로 서빙하였고(가중치 해시 확인은 Qwen3만), 입력은 트랙 프롬프트와 기반 파일을 담은 메시지 하나이다(시스템 프롬프트·도구 없음, temperature 0.7).

에이전트 조건은 Claude Code 2.1.291(claude-opus-5-5)에 트랙 A의 같은 입력을 주어 격리 환경에서 기본 도구(파일, 셸; 웹·MCP 차단)로 실행하였다(채점·피드백 동일, 표본 1건, 제출 없이 끊긴 시작 2회 제외). 도구·사고 예산이 달라 모델 비교가 아닌 절차 관찰용이며, 절차는 이벤트 기록과 작업 파일로 재구성하였다(사고 본문 미기록).

### 2. 물리 시뮬레이션 판정 결과

1회차 60건(모델·가속기당 트랙 A·B 각 5건)은 정적 검증을 모두 통과하였으나(21건은 끼워 넣은 뒤) 물리 실행 통과는 0건이었다(표 1). 실패는 저평면 충돌 10, 가시 충돌 35(주로 경로 초반의 상자 00·01), 정지 13, 실행 오류 2건(표 1 주)이었고, 가속기 간 실패 분포(GPU 6·17·7·0, NPU 4·18·6·2)와 루프 통과(1 대 0)는 구별되지 않았다. 1회차·상한 8 루프(2회차 이후)·이식 조건(4절)의 저평면 충돌 42건(각 10·18·14건) 중 원문이 남은 41건은 모두 상자 표·좌표 없이 기본 높이의 스캔만 호출하여 부딪힌 장애물의 정보를 얻지 못하였다(정보가 있었다면 피하였을지는 시험하지 않음). 회차 루프(gpt-oss-120b, 가속기당 트랙 A 5·B 1실행, 93회차)의 통과는 GPU 트랙 A 1실행(5회차)뿐이었고, 그 코드도 충돌 피드백이 알려 준 상자 06의 좌표를 상자 표에서 옮겨 하드코딩했을 뿐 높이와 스캔을 연결하지 않았다. 1회차와 상한 8 루프의 트랙 A 응답 중 원문이 남은 90건을 수동 판정한 결과, 상자 높이와 스캔 평면을 연결한 응답은 없었다.

### 3. 코딩 에이전트의 작업 절차

Claude는 1회차에 통과하였다(최종 거리 0.10 m, 접촉 0, 도달 39.75 s; 90분, 도구 98회). 기록을 여섯 단계로 나누면(표 2), 20분의 첫 초안 머리 주석에 이미 "Four boxes are lower than the default z=0.35 scan plane, so they are known only from MISSION"이라는 판단이 있었다. 이어 높이를 반영해 저평면 충돌을 판정하는 자작 시뮬레이터로 108개 상황을 통과시킨 뒤, 회귀 시험과 바이트 대조를 거쳐 제출하였다.

### 4. 절차 요인의 이식

옮기는 것은 절차이며 내용이 아니므로 결론("상자 표를 지도로")과 높이별 센서 모델은 정답 누설로 보고 뺐다. 기준 T0(회차 루프의 NPU 트랙 A 5실행)에 요소를 한 겹씩 더하였다. T3(숙고, 단계 ①)은 reasoning_effort=high(5실행), T2(자기 검증 수단, ③~⑥)는 T3 + Python 실행 도구·안내(회차당 도구 12회, 3실행)이다. T2P(작업 순서, ①~⑥)는 T2의 안내 대신 에이전트의 작업 순서를 담은 11단계 지시문(12,322자)과 기반 파일 원문, 회차당 도구 28회·6시간을 주고, 시험 기록·최종 확인·제출 파일 중 하나라도 갱신되지 않은 회차의 최종 답을 한 번 반려한다(3실행). T2P는 지시와 예산이 함께 바뀐 묶음 조건이며, 덧붙인 문구는 실행 전 누설 감사를 거쳤다.

**표 2. 에이전트의 작업 단계와 T2P의 이행**
**Table 2. Agent work stages and T2P execution**

| 단계 | 에이전트 | T2P (3실행) |
|---|---|---|
| ① 숙고 | 13분간 77,846 토큰 | 메모 3/3(갱신 0) |
| ② 첫 초안 | 저평면 판단·상자 지도 | 올바른 연결 0 |
| ③ 시뮬레이터 | 상자·스캔 높이 반영 | 2/3, 높이 없는 2D |
| ④ 시험 묶음 | 108/108 | 0 |
| ⑤ 원인·회귀 | 실패 사례 재현 | 0 |
| ⑥ 조립 | 바이트 대조 | 스크립트 3/3 |

통과는 T0 0/5, T3 1/5(8회차; 2실행은 빈 응답으로 조기 종료), T2 0/3, T2P 0/3이며, 표본이 작아 요인의 효과로 단정하지 않는다. T3은 추론 토큰을 약 14배로 늘렸으나 높이–스캔 연결은 없었고, 통과한 실행은 충돌 피드백을 거쳐 상자 표 기반 지도에 도달하였다. T2의 도구 호출은 8회였고 상자 배치를 담은 시험은 없었다. T2P의 도구 호출은 394회였으나 시뮬레이터를 만든 두 실행은 상자를 높이 없는 2D로 넣었고(한 실행의 주석: "For simplicity, ignore z") 시뮬레이터 파일의 실행 2회는 모두 오류였으며, 최종 답은 24개 회차 중 16개에서 반려되었고 정적 실격도 6회였다. 즉 메모·조립·도구 호출 같은 형식은 옮겨졌지만(표 2), 명세를 읽어 낸 판단이 없던 실행은 명세를 담은 검증 환경을 만들지 못했고 높이를 버린 시뮬레이터로는 저평면 장애물을 놓치는 충돌을 재현할 수 없었다. 다만 에이전트의 판단은 시뮬레이터보다 먼저 있었고 표본이 1건이라 그 검증의 기여는 가릴 수 없으며, 유일한 통과(T3)도 피드백을 거친 탐색에서 나왔다.

## Ⅲ. 결 론

본 논문은 공개 가중치 LLM의 로봇 제어 코드를 물리 실행으로 판정하여, 정적 검증을 모두 통과한 1회차 코드 60건이 한 건도 통과하지 못하였고 1회차·상한 8 루프의 트랙 A 응답 90건 중 상자 높이와 스캔 평면을 연결한 응답이 없었음을 보였다. 에이전트의 절차를 NPU 서빙 모델에 이식하자 메모·조립·잦은 도구 호출 같은 형식은 옮겨졌으나 시험 묶음과 명세를 담은 자기 검증 환경은 옮겨지지 않았다. 이는 서빙 모델로 제어 코드를 만드는 임베디드 현장에 물리 실행 판정과, 모델이 정답 누설 없이 명세를 담은 검증 환경을 갖추게 할 방법이 필요함을 시사한다. 본 연구는 단일 환경, 조건당 5실행 이하, 에이전트 1실행의 결과이다. 제어기의 감각은 잡음 없는 가상 스캔과 참값 자세로 이상화되었고, 스캔 함수는 PhysX가 먼저 보고한 면을 돌려주어 빈 바닥 1,552곳에서 쏜 빔의 2.6%가 가장 가까운 면보다 먼 거리를 반환하였다(그중 63개는 가장 가까운 면이 상자 00·01이라 가시 충돌 일부에 작용했을 수 있음). 향후 실제 라이다·카메라 데이터로 분석을 반복하고, 검증 환경을 갖추게 하는 조건과 공개 모델로 구동한 에이전트를 더 많은 표본으로 시험할 계획이다.

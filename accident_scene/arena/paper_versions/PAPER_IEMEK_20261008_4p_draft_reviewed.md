**An Analysis of LLM Robot-Control Code Generation in Physics Simulation and of a Coding Agent's Work Procedure**

**요약 :** 대규모 언어 모델(LLM)이 작성한 로봇 제어 코드는 코드 수준 검사를 통과해도 물리 환경에서 실패할 수 있다. 본 논문은 Nova Carter 로봇의 60 Hz 제어 함수를 작성하는 과제와, 생성 코드를 정적 검증과 Isaac Sim 물리 실행으로 판정하는 평가 환경을 구축하였다. 상자 14개 중 4개는 거리 스캔 평면(0.35 m)보다 낮으며, 상자 높이와 스캔 높이는 모두 입력에 주어진다. GPU와 NPU에서 서빙한 공개 가중치 모델 3종(gpt-oss-120b, Qwen3-32B, EXAONE-4.0-32B)의 1회차 코드 60건은 정적 검증을 모두 통과하였으나 물리 실행 통과는 0건이었고, 판정을 되돌려주는 회차 루프에서도 gpt-oss-120b는 12개 실행 중 1개만 통과하였다. 응답 90건 중 상자 높이와 스캔 평면을 연결한 응답은 없었다. 같은 입력을 받은 코딩 에이전트 Claude Code는 1회 실행에서 1회차에 통과하였다. 작업 절차를 분해하면, 낮은 상자는 상자 표로만 알 수 있다는 판단이 시험 전의 첫 초안에 이미 있었고, 에이전트는 높이를 반영한 자작 시뮬레이터에서 108개 상황을 시험하였다. 이 절차의 요소를 NPU 서빙 gpt-oss-120b에 한 겹씩 이식하자 숙고 조건만 5회 중 1회 통과하였고, 그것도 높이와 스캔 평면을 연결하지 않은 채 충돌 피드백을 거쳐 도달한 것이었다. 작업 순서를 지시하자 도구 호출은 숙고+도구 조건의 약 50배로 늘었으나, 시뮬레이터는 높이를 버린 2D였고 시험 묶음은 만들어지지 않았다. 절차의 일부 형식은 옮겨졌으나 명세를 담은 자기 검증 환경은 옮겨지지 않았다. 이는 단계를 지시하는 것만으로는 부족하고, 명세를 담은 검증 환경을 갖추게 하는 방법이 필요함을 시사한다.

## Ⅰ. 서 론

대규모 언어 모델(LLM)이 자연어 지시로부터 로봇 제어 코드를 생성하는 접근이 확산되고 있다[1]. 생성 코드는 흔히 코드 수준 검증으로 평가되지만, 제어 코드의 성패는 센서 특성과 접촉이 작용하는 물리 환경에서 실행해야 드러난다. 이를 판정하는 데 Isaac Sim[2] 같은 물리 시뮬레이터를 쓸 수 있다.

코딩 에이전트는 모델을 한 번 호출해 코드를 받는 방식과 달리, 숙고하고 파일을 만들어 실행하며 스스로 시험한 뒤 제출하는 작업 절차를 거친다. 같은 과제에서 에이전트는 통과하고 단일 호출 모델은 실패한다면, 절차의 어느 요소가 그 차이를 만드는지가 질문이 된다. 이는 데이터를 외부로 보내지 않으려고 공개 가중치 모델을 GPU(vLLM[3])나 NPU(RNGD[4])에서 서빙하는 현장에서, 서빙 모델에 에이전트의 절차를 옮길 수 있는가의 문제이기도 하다.

본 논문은 LLM이 작성한 로봇 제어 코드를 물리 시뮬레이션으로 판정한다. 또한 같은 입력을 통과한 코딩 에이전트의 작업 절차를 단계로 분해하고, 그 요소를 NPU 서빙 공개 모델에 한 겹씩 이식하여 어느 요소가 물리 실행 통과로 이어지는지 분석한다. 본 논문의 기여는 다음과 같다.

- 판단에 필요한 정보를 모두 공개한 저평면 장애물 과제와, 정적 검증과 물리 실행을 나누어 판정하는 평가 환경을 구축하였다.
- GPU·NPU에서 서빙한 공개 가중치 모델 3종의 생성 코드를 물리 실행으로 판정하여, 정적 검증과의 간극과 명세 연결의 부재를 측정하였다.
- 코딩 에이전트의 작업 절차를 단계로 분해하고 그 요소를 공개 모델에 이식하여, 어떤 요소가 옮겨지고 어떤 요소가 옮겨지지 않는지 분석하였다.

## Ⅱ. 본 론

### 1. 문제 정의

평가 과제는 Isaac Sim 창고 장면에서 차동 구동 로봇 Nova Carter를 남서 모서리 (−9.0 m, −10.8 m)에서 북동 모서리 (8.0 m, 16.5 m)까지 주행시키는 것이다(그림 1(a)). 그 사이에 상자 14개와 상자 표에 없는 고정 구조물(벽, 선반, 지게차)이 있다. 입력은 트랙 프롬프트와 기반 파일(base_carter_run.py)뿐이며, 모델은 기반 파일의 수정 구역만 고쳐 60 Hz 제어 함수 controller(t, pose, env) → (v, w, done)을 작성한다. 제어기는 참값 자세를 받으며, 외부 감각은 env.raycast_scan()뿐이다. 이는 높이 z = 0.35 m의 수평면에서 전방 180°에 광선 61개를 쏘는 잡음 없는 가상 2D 거리 센서(PhysX 광선 질의)이고, 로봇 모델의 라이다·카메라 데이터는 주지 않는다. 판정은 고정 하네스가 하며, 120 s 안에 목표 0.75 m·yaw 0.26 rad 이내에 멈추고 상자·지게차·선반과의 접촉이 0이면 통과이다.

기반 파일의 상자 표는 상자 14개의 위치·크기·높이를 명시한다. 상자 04·05·06·13은 높이가 0.18~0.25 m로 스캔 평면보다 낮다(저평면 장애물, 그림 1(b)). Isaac Sim에서 각 상자의 1 m 밖에서 z = 0.35 m 광선을 쏘면, 높이 1.0 m 상자 10개는 모두 검출되고 저평면 장애물 4개는 하나도 검출되지 않는다. 목표 방향을 막는 상자 03의 동쪽 끝 우회로는 상자 04·05가 막는다. 상자 높이와 스캔 높이가 같은 입력에 평문으로 있어 대소 비교만으로 귀결이 나오므로 은닉 정보가 아니며, 0.6 m 여유의 경로(34.7 m)도 있다. 낮은 상자를 알고 피하려면 상자 표를 지도로 쓰거나 스캔 높이를 낮춰야 한다. 주 실험은 상자 표 사용을 허용하는 트랙 A이며, 상자 표 참조와 좌표 하드코딩을 금지하는 트랙 B는 보조로 둔다.

### 2. 실험 환경

물리 실행은 Isaac Sim 4.5에서 직렬로 수행하며, 그 전에 정적 검증(구문, 수정 구역 밖 바이트 동일성, 트랙 B 규칙, controller() 정의)을 거친다(표 1). 트랙 B 규칙은 상자 표·배치 정보의 참조와 좌표 쌍 4개 이상의 상수를 위반으로 보며, 이 기준은 실험 전에 정하였다. 공개 가중치 모델 3종을 GPU와 NPU에서 같은 모델명으로 서빙하였다(가중치 해시 확인은 Qwen3만). 입력은 메시지 하나이며 시스템 프롬프트와 도구는 주지 않는다. 실패하면 같은 대화에 판정 결과를 덧붙여 재제출을 받으며(회차 루프, 상한 8회차), 정적 실격과 실행 오류도 한 회차로 세고, 응답에 본문이 없으면 그 실행을 끝낸다(그림 2).

에이전트 조건에서는 Claude Code(claude-opus-5-5)에 트랙 A의 같은 입력을 주고, 빈 작업 폴더만 보이는 격리 환경에서 기본 도구(파일, 셸)로 실행하였다. 채점·피드백·상한은 같다. 시스템 프롬프트·도구·사고 예산이 달라 모델 비교가 아니라 작업 절차의 관찰에 쓰며, 이벤트 기록과 작업 파일로 절차를 시간대별로 재구성하였다(사고 본문은 기록되지 않음). 유효 표본은 1건이다.

### 3. 물리 시뮬레이션 판정 결과

1회차 60건(모델·가속기당 트랙 A·B 각 5건)은 정적 검증을 모두 통과하였으나 물리 실행 통과는 0건이었다(표 2). 실패는 저평면 충돌 10, 가시 충돌 35, 정지 13, 실행 오류 2건이며, 가시 충돌의 상대는 대부분 경로 초반의 높이 1.0 m 상자 00·01이었다. 1회차·회차 루프·이식 조건의 저평면 충돌 42건 중 원문이 남은 41건은 모두 상자 표를 쓰지 않고 기본 높이의 스캔만 호출하였다. 즉 이 충돌에서 제어기는 부딪힌 저평면 상자의 정보를 얻지 못하였다. 다만 정보가 있었다면 피하였을지는 시험하지 않았다.

회차 루프(gpt-oss-120b, 가속기당 트랙 A 5·트랙 B 1실행, 93회차)에서 통과는 GPU 트랙 A의 1실행(5회차)뿐이었고, 정적 실격 7회는 모두 수정 구역 밖의 문장부호를 유니코드 문자로 바꿔 쓴 경우였다. 이 코드도 피드백이 알려 준 충돌 상자의 좌표를 상자 표에서 옮겨 경유점을 하드코딩한 것으로, 높이와 스캔을 연결하지 않았다. 상한을 30회차로 둔 NPU 별도 1실행도 통과하지 못하였다. 1회차와 상한 8 루프의 트랙 A 응답 90건을 수동으로 판정한 결과, 상자 높이와 스캔 평면을 연결한 응답은 없었다(상한 30 실행의 29건 중 1건은 연결했으나 검출된다고 잘못 판단).

가속기 간에는 1회차 실패 분포와 회차 루프 통과(트랙 A 5실행 중 1 대 0)에서 차이가 구별되지 않았다. 요청 단위 처리량은 모델에 따라 우열이 뒤집혔고(gpt-oss-120b는 GPU가 6.3배, Qwen3는 NPU가 1.25배), 회차 지연 중앙값은 GPU 63.0 s, NPU 115.1 s로 차이는 생성 시간에서 왔다. 카드 수가 달라(1장 대 4장) 구성 단위로만 비교한다.

### 4. 코딩 에이전트 작업 절차 분석

#### 4.1 동일 입력 실행의 작업 절차

Claude는 1회차에 통과하였다(최종 거리 0.10 m, 접촉 0, 도달 39.75 s). 90분 동안 도구를 98회 호출하였고 서브에이전트는 쓰지 않았다. 표 3은 기록을 여섯 단계로 나눈 것이다. 첫 도구 호출(13분) 전까지 출력 77,846 토큰을 냈고, 20분의 첫 초안 머리 주석에는 이미 "Four boxes are lower than the default z=0.35 scan plane, so they are known only from MISSION"이라는 판단이 있었다. 이어 만든 자작 시뮬레이터는 상자의 높이 범위와 스캔 높이를 반영하여, 스캔 평면 아래 물체를 놓치는 제어기를 실패로 판정할 수 있었다. 에이전트는 이 위에서 108개 시나리오를 통과시키고 실패 시드의 원인을 가린 뒤, 수정 구역을 기반 파일에 끼워 바이트 대조로 제출하였다.

| ⑥ 조립·확인 (89–90분) | 기반 파일에 끼워 바이트 대조 | 조립 스크립트 3/3, 정적 실격 6 |

#### 4.2 절차 요인의 이식

옮기는 것은 절차이며 내용이 아니다. "상자 표를 지도로 쓴다"는 결론이나 높이별 센서 모델은 정답 누설이므로 뺐다. 회차 루프의 NPU 트랙 A 5실행(T0)에 다음을 한 겹씩 더하였다.
- T3(숙고, 단계 ①): 요청 필드 reasoning_effort=high. 5실행.
- T2(자기 검증 수단, 단계 ③~⑥): T3 + Python 실행 도구와 사용 안내. 3실행.
- T2P(작업 순서, 단계 ①~⑥): T2의 안내 대신 에이전트의 작업 순서를 담은 11단계 지시문(12,322자), 작업 폴더의 기반 파일 원문, 회차당 도구 28회·6시간. 필수 파일이 없으면 하네스가 최종 답을 반려한다. 3실행.

T2P는 지시와 예산이 함께 바뀐 묶음 조건이다. 덧붙인 문구는 실행 전에 누설 감사를 거쳤고, 판정 전에 끊긴 생성은 같은 상태에서 다시 생성하였다.

#### 4.3 이식 결과

T3은 5회 중 1회(8회차) 통과하였고 T2·T2P는 각각 3회 중 0회였다(표 4). T3은 추론 토큰을 약 14배로 늘렸으나 높이와 스캔을 연결한 응답은 없었고, 두 실행은 출력 한도에 걸린 응답이 본문 없이 반환되어 3·6회차에 끝났다. 통과한 실행은 충돌 피드백을 거쳐 상자 표 기반 지도에 도달하였다. T2에서 도구는 24개 회차 중 5개 회차에서 8회 쓰였고, 상자 배치를 담은 시험은 없었다. T2P에서 도구 호출은 394회로 늘었으나, 시뮬레이터 파일을 만든 두 실행은 모두 높이를 버린 2D로 상자를 넣었고("For simplicity, ignore z") 그 파일의 실행은 모두 오류였다. 시험 묶음은 만들어지지 않았다. 필수 파일 없이 최종 답을 내 반려된 회차가 24회차 중 16이었고, 정적 실격 6회 중 4회는 그 회차의 제출 파일을 저장하지 못한 경우였다.

두 계열을 단계별로 맞대면 차이는 단계의 유무와 내용 모두에 있었다. 에이전트의 시뮬레이터는 앞서 읽어 낸 명세를 담았으나, T2P의 시뮬레이터는 같은 순서의 지시 아래에서도 높이를 버려 스캔이 낮은 상자를 놓치는 충돌을 재현할 수 없었다. 메모·조립·도구 호출 같은 형식은 옮겨졌지만 명세를 담은 검증 환경은 만들어지지 않았고, 유일한 통과(T3)도 피드백을 거친 탐색에서 나왔다.

## Ⅲ. 결 론

본 논문은 공개 가중치 LLM이 작성한 로봇 제어 코드를 물리 시뮬레이션으로 판정하여, 정적 검증을 모두 통과한 1회차 코드 60건이 물리 실행에서는 한 건도 통과하지 못하고, 응답 어디에서도 상자 높이와 스캔 평면이 연결되지 않았음을 보였다. 같은 입력을 통과한 코딩 에이전트의 절차를 분해하고 그 요소를 NPU 서빙 모델에 이식한 결과, 설계 메모·조립·잦은 도구 호출 같은 형식은 옮겨졌으나 시험 묶음과 명세를 담은 자기 검증 환경은 옮겨지지 않았다. 이는 단계를 지시하는 것만으로는 부족하며, 정답 누설 없이 명세를 담은 검증 환경을 갖추게 하는 방법이 필요함을 시사한다.

본 연구는 단일 주행 환경, 조건당 5실행 이하, 에이전트 1실행에 기반하며, 에이전트 실행은 도구·사고 예산이 달라 모델 비교가 아니다. T2P는 묶음 조건이며, 누설을 막기 위해 에이전트 시뮬레이터의 높이별 센서 모델은 옮기지 않았다. 숙고 조건의 두 실행은 빈 응답으로 상한보다 일찍 끝났다. 제어기의 감각은 잡음 없는 가상 스캔과 참값 자세로 이상화되었고, 하네스의 스캔은 PhysX가 먼저 보고한 면을 돌려주어 표본 빔의 2.6%에서 가장 가까운 면보다 먼 거리를 반환하였다. 향후에는 로봇에 실린 실제 라이다·카메라 데이터와 센서 기반 위치 추정을 제어기에 주어 같은 분석을 반복하고, 명세를 담은 검증 환경을 제공하는 조건과 공개 모델을 에이전트 하네스에 넣는 조건을 더 많은 표본으로 시험할 계획이다.

**요약 :** 대규모 언어 모델(LLM)이 작성한 로봇 제어 코드는 코드 수준 검사를 통과해도 물리 환경에서 실패할 수 있다. 본 논문은 Nova Carter 로봇을 60 Hz로 제어하는 함수를 작성하는 과제와, 생성 코드를 정적 검증과 Isaac Sim 물리 실행으로 나누어 판정하는 평가 환경을 구축하였다. 상자 14개 중 4개는 높이가 0.18~0.25 m로 거리 센서의 기본 스캔 평면(0.35 m)보다 낮으며, 두 값은 모두 입력에 평문으로 주어진다. 공개 가중치 모델 3종을 GPU와 NPU에서 서빙하여 얻은 1회차 코드 60건은 정적 검증을 모두 통과하였으나 물리 실행 통과는 0건이었고, 가속기 간 차이도 구별되지 않았다. 판정을 되돌려주는 회차 루프(상한 8)에서도 gpt-oss-120b는 12개 실행 중 1개만 통과하였고, 1회차와 이 루프의 트랙 A 응답 90건 중 상자 높이와 스캔 평면을 연결한 응답은 없었다. 같은 입력을 받은 코딩 에이전트 Claude Code는 1회 실행에서 1회차에 통과하였다. 그 작업 절차를 분해한 결과, 상자 4개는 기본 스캔 평면보다 낮아 상자 표로만 알 수 있다는 판단은 숙고를 거쳐 시험 전에 쓴 첫 초안(20분)에 이미 있었고, 에이전트는 상자 높이를 반영한 자작 시뮬레이터에서 108개 상황을 시험하였다. 이 절차의 요소를 NPU 서빙 gpt-oss-120b에 한 겹씩 이식하자, 숙고 조건은 5회 중 1회 통과하였으나, 상자 높이와 스캔 평면을 연결하지 않은 채 충돌 피드백을 거쳐 도달한 것이었다. 숙고+도구 조건(3회 중 0회)에서는 도구가 거의 쓰이지 않았다. 작업 순서 지시 조건(3회 중 0회)에서는 도구 호출이 숙고+도구 조건의 약 50배(24회차 합계 8회 → 394회)로 늘었으나, 시뮬레이터는 3실행 중 2실행만 만들었고 둘 다 높이를 버린 2D였으며 시험 묶음은 만들어지지 않았다. 설계 메모·조립·잦은 도구 호출 같은 절차의 일부 형식은 옮겨졌으나, 시험 묶음, 그리고 명세를 담은 자기 검증 환경은 옮겨지지 않았다.

## Ⅰ. 서 론

대규모 언어 모델(LLM)이 자연어 지시로부터 로봇 제어 코드를 직접 생성하는 접근이 확산되고 있다[1]. 생성 코드는 흔히 구문·규약 검사 같은 코드 수준 검증으로 평가된다. 그러나 제어 코드의 성패는 센서 특성과 접촉이 작용하는 물리 환경에서 실행해야 드러난다. 이를 판정하는 데 Isaac Sim[2] 같은 물리 시뮬레이터를 쓸 수 있다.

코딩 에이전트는 모델을 한 번 호출해 코드를 받는 방식과 다르다. 에이전트는 숙고하고, 파일을 만들어 실행하고, 스스로 시험한 뒤 제출하는 작업 절차를 거친다. 같은 과제에서 에이전트는 통과하고 단일 호출 모델은 실패한다면, 절차의 어느 요소가 물리적으로 올바른 코드를 만들었는지 물을 수 있다. 이 질문은 실무와도 닿아 있다. 로봇·임베디드 현장에서는 데이터를 외부로 보내지 않으려고 공개 가중치 모델을 온프레미스 가속기에서 서빙하려는 수요가 있다. 같은 모델을 GPU에서는 vLLM[3]으로, NPU인 RNGD[4]에서는 전용 서빙 스택 furiosa-llm으로 운용할 수 있다. 이렇게 서빙한 모델에 에이전트의 절차를 옮겨 부족한 부분을 보완할 수 있는지가 관심사가 된다.

본 논문은 LLM이 작성한 로봇 제어 코드를 물리 시뮬레이션으로 판정한다. 또한 같은 입력을 통과한 코딩 에이전트의 작업 절차를 기록하여 단계로 분해한다. 이어 그 단계의 요소를 NPU 서빙 공개 모델에 한 겹씩 이식하여, 어느 요소가 물리 실행 통과로 이어지는지 분석한다. 본 논문의 기여는 다음과 같다.

- 저평면 장애물 과제를 계획(트랙 A)·반응(트랙 B) 두 트랙으로 정의하고, 저평면 장애물 판단에 필요한 정보(상자 높이와 스캔 높이)를 모델 입력에 모두 공개하였다. 정적 검증과 물리 실행을 나누어 판정하는 평가 환경을 구축하였다.
- 공개 가중치 모델 3종을 GPU·NPU에서 서빙하여 1회차 60건과 gpt-oss-120b 회차 루프 93회차(1회차 12건은 앞의 60건과 공유)를 정적 검증과 물리 실행으로 판정하였다. 정적 검증 통과와 물리 실행 통과 사이의 간극과, 응답이 명세를 연결하지 못함을 측정하였다.
- 동일 입력 코딩 에이전트 실행의 작업 절차를 시간·도구·산출물 단위로 분해하였다. 숙고, 자기 검증 도구, 작업 순서 지시를 NPU 서빙 gpt-oss-120b에 이식하여 물리 실행으로 판정하였다. 그 결과 이번 표본에서는 설계 메모·조립 같은 절차의 일부 형식은 옮겨졌으나, 시험 묶음, 그리고 명세를 담은 자기 검증 환경은 옮겨지지 않았다.

## Ⅱ. 본 론

### 1. 문제 정의

#### 1.1 주행 과제와 성공 조건

평가 과제는 Isaac Sim 창고 장면에서 차동 구동 로봇 Nova Carter를 주행시키는 것이다. 출발 자세는 남서 모서리의 (−9.0 m, −10.8 m, 1.0138 rad), 목표 자세는 북동 모서리의 (8.0 m, 16.5 m, 1.0138 rad)이다(그림 1(a)). 두 자세의 직선거리는 약 32 m이다. 그 사이에 정적 상자 14개와 상자 표에 없는 고정 구조물(벽, 기둥, 선반, 지게차)이 있다.

과제 입력은 트랙 프롬프트와 기반 파일 base_carter_run.py뿐이다. 모델은 기반 파일의 [EDIT REGION] 블록(이하 수정 구역)만 고쳐 controller(t, pose, env) → (v, w, done)을 작성한다. 제어기는 1/60 s마다 섀시의 참값 자세 pose = (x, y, yaw)를 받아 전진 속도 v와 각속도 w를 ROS 2 /cmd_vel로 낸다. 제어기가 받는 외부 감각은 env.raycast_scan(n_beams=61, fov_deg=180.0, z=0.35, max_range=6.0)뿐이다. 이는 PhysX 광선 질의로 만든 잡음 없는 2D 거리 센서로, 높이 z의 수평면에서 광선 61개를 쏘아 맞은 면까지의 거리를 돌려준다. 로봇 모델에 실린 라이다·카메라의 데이터는 제어기에 주지 않는다. 이하에서 '검출'은 이 스캔에 잡히는 것을 뜻한다. 다른 파일 열람, import 추가, 시뮬레이터 직접 실행은 금지된다.

판정은 제출 파일 밖의 고정 하네스가 한다(제어기가 받는 env는 하네스 객체이나, 제출 코드는 모두 env.raycast_scan만 호출하였다). 주행은 done 반환 또는 120 s(모의 시간) 경과로 끝난다. 1 s 정지 후의 최종 자세와 접촉 이벤트 수(collision_count)가 표 1의 세 조건을 모두 만족하면 통과이다. collision_count는 물리 스텝마다 집계한 섀시 접촉 보고 수이며, 로봇 자신·바닥·창고 건물 모델(벽·기둥·랙·팔레트)과의 접촉은 집계에서 제외한다. 첫 접촉 5 s 후 주행을 중단하고 이어지는 1 s 정지 구간까지 집계하므로 값은 그 시점에서 잘린다(지속 접촉 1건이면 6 s × 60 스텝 = 360).

#### 1.2 저평면 장애물과 트랙

기반 파일의 MISSION 표는 상자 14개의 위치·크기·높이를 명시한다. 같은 파일의 docstring은 센서를 z = 0.35 m의 수평 레이 팬으로 기술한다. 상자 10개는 높이 1.0 m라 이 평면에 걸린다. 반면 상자 04(0.25 m), 05(0.20 m), 06(0.18 m), 13(0.20 m)은 평면보다 낮아 기본 스캔 평면(z = 0.35 m)의 빔에는 검출되지 않는다(그림 1(b)). 이를 저평면 장애물이라 한다. Isaac Sim 장면에서 각 상자의 1 m 밖에서 z = 0.35 m 수평 광선을 쏘아 확인한 결과, 높이 1.0 m 상자 10개는 모두 검출되었으나 저평면 장애물 4개는 하나도 검출되지 않았다(상자 04 쪽 광선은 그 위를 지나 뒤쪽 상자 03에 맞았다). 높이 1.0 m인 상자 03이 목표 방향 직선을 막고, 그 동쪽 끝에 상자 04·05가 붙어 있다. 그래서 보이는 끝을 돌아가는 우회로가 저평면 장애물에 막힌다. 상자 06은 목표 직전의 직선 접근로를 가로막는다. 그러나 모든 상자와 구조물을 0.6 m 여유로 팽창시킨 2D A* 탐색에서도 길이 34.7 m의 경로가 있으므로 과제는 풀 수 있다.

저평면 장애물은 고정 높이 스캔에 잡히지 않는 팔레트·도크 턱 같은 낮은 물체를 모사한다. 이를 알고 피하려면 (가) 상자 표를 지도상 장애물로 쓰거나 (나) raycast_scan의 z 인자로 스캔 평면을 낮춰야 한다(경로에 따라서는 모르고 비켜 갈 수도 있다). 상자 높이와 스캔 높이는 같은 입력 파일에 평문으로 있고, 대소 비교만으로 귀결이 나온다. 따라서 은닉 정보가 아니며, 본 과제는 주어진 명세가 제어 코드로 연결되는지를 잰다. 트랙 A는 상자 표를 읽어 경로를 계획하는 것을 허용한다. 트랙 B는 상자 표 참조와 좌표·배치 하드코딩을 모두 금지하므로 (나)만 쓸 수 있다. 두 트랙은 재는 능력이 달라 수치를 비교하지 않으며, 주 실험은 트랙 A로 수행한다.

### 2. 실험 환경 구축

#### 2.1 시뮬레이터와 정적 검증

물리 실행은 Isaac Sim 4.5.0에서 수행한다(표 2). 타이밍 변동을 줄이려고 실행기가 동시 실행을 차단하며, 모든 채점은 직렬로 수행하였다. 물리 실행 전에는 정적 검증으로 다음 네 가지를 차례로 검사한다. (i) 구문 분석, (ii) [EDIT REGION] 밖의 기반 파일과의 바이트 동일성, (iii) 트랙 B에서 상자 표·배치 정보를 참조하거나 좌표 쌍 4개 이상을 상수로 적었는지(상자 좌표와 우연히 가까운 단일 수치는 위반으로 보지 않으며, 이 기준은 본 실험 전에 정하였다), (iv) controller() 정의 여부이다. 하나라도 어기면 시뮬레이터를 실행하지 않고 정적 실격으로 집계한다.

#### 2.2 모델 서빙

공개 가중치 모델 3종(gpt-oss-120b, Qwen3-32B-FP8, EXAONE-4.0-32B-FP8)을 GPU와 NPU에서 같은 모델명으로 서빙하였다(GPU는 공개 저장소 ID, NPU는 서버 등록명으로 요청). 가중치 동일성은 Qwen3-32B-FP8에 대해서만 확인하였다. furiosa-ai 재배포본과 상류 배포본의 sha256이 일치하였다(7/7 샤드). gpt-oss-120b는 GPU에서 openai/gpt-oss-120b(MXFP4)를 로드했으며, gpt-oss·EXAONE의 가속기 간 동일성은 검증되지 않았다. 입력은 트랙 프롬프트와 기반 파일을 이은 메시지 하나뿐이며, 시스템 프롬프트와 도구는 주지 않는다. furiosa-llm은 소스 코드상 요청의 seed를 샘플링에 쓰지 않는 것으로 보이나 실측으로 확인하지 않았으므로, NPU 표본은 독립 추출로 취급한다. 카드 수가 다르므로(4장 대 1장) 가속기의 장당 성능은 비교하지 않는다.

#### 2.3 회차 루프

#### 2.4 에이전트 실행과 작업 절차 기록

동일 입력 조건에서는 Claude Code 에이전트(claude-opus-5-5)에 트랙 A의 같은 입력을 첫 메시지로 주고 bubblewrap 격리 환경에서 실행한다. 격리 환경에서는 빈 작업 폴더와 빈 임시 폴더, 읽기 전용 시스템 디렉터리만 보이며, 프로젝트 파일·사용자 메모리·Isaac Sim은 보이지 않는다. 파일 읽기·쓰기, 셸, 서브에이전트 같은 기본 도구는 허용하고, 웹 검색·웹 가져오기와 MCP 서버는 끈다. 정적 검증·채점·피드백 문구·상한 8회차는 2.3절과 같다. 다만 회차 간에 같은 세션을 이어 가므로 6만 자 대화 절단은 적용되지 않는다. 작업 절차는 에이전트의 이벤트 스트림과 세션 전사(에이전트가 쓴 문장, 도구 호출과 결과, 시각, 토큰 사용량), 작업 중 만든 파일로 기록하였고, 이를 시간대별로 재구성하여 단계로 나누었다. 사고 본문은 기록되지 않아 숙고 단계는 경과 시간과 사고 토큰 수로만 파악하였다. 시스템 프롬프트·도구·사고 예산·샘플링이 공개 모델과 다르므로 이 실행은 모델 비교가 아니라 작업 절차의 관찰에 쓴다. 표본은 1건이다. 이 실행 전의 시작 2회는 에이전트의 제출 없이 끊겨(세션 재시작 1회, 구독 사용 한도 1회) 무효로 처리하였다. 2026년 9월에 같은 과제를 통과한 Claude 기록은 과제 프롬프트 밖의 유도 문장과 구판 프롬프트를 받는 등 입력이 달라 분석에서 제외하였다.

### 3. 물리 시뮬레이션 판정 결과

#### 3.1 1회차 결과

표 3은 1회차 코드 60건(모델·가속기당 트랙 A·B 각 5건)의 판정이다. 60건은 정적 검증을 모두 통과하였다. 이 중 21건은 수정 구역만 출력하여 기반 파일에 끼워 넣은 뒤 검사하였다. 그러나 물리 실행 통과는 0건이었다. 여섯 조합이 모두 10건 중 0건이므로 1회차 통과로는 모델 간 순위가 성립하지 않는다.

실패는 네 가지로 분류하였다. 저평면 충돌은 접촉 상대에 저평면 상자(04·05·06·13)가 하나라도 있는 경우, 가시 충돌은 그 밖의 물체(높이 1.0 m 상자, 지게차 등)와만 접촉한 경우이다(상자 03·04에 함께 접촉한 1건은 저평면으로 셌다). 정지는 접촉은 없으나 최종 위치·yaw 조건을 만족하지 못한 경우(회차 루프에서 위치는 맞고 yaw만 틀린 1회 포함), 실행 오류는 컨트롤러 예외로 중단된 경우이다. 60건은 저평면 충돌 10건, 가시 충돌 35건, 정지 13건, 실행 오류 2건이다. 가시 충돌 35건의 첫 접촉 대상은 경로 초반의 높이 1.0 m 상자 00(27건)·01(7건)과 지게차 포크(1건)이다. EXAONE의 저평면 충돌 0건은 회피의 근거가 아니다. 궤적이 남은 18건 중 17건이 저평면 상자에서 2 m 이상 떨어져 주행하였다. 실행 오류 2건(NPU, EXAONE)은 모두 UnboundLocalError로, 정적 검증을 통과한 코드가 실행 중 중단된 사례이다. 1회차·상한 8 회차 루프(2회차 이후)·이식 조건(4장)의 저평면 충돌 42건(각 10·18·14건) 중 코드가 남은 41건은 모두 상자 표나 상자 좌표를 쓰지 않고 기본 높이(0.35 m)의 스캔만 호출하였다(1건은 기록 손실로 원문이 없다). 따라서 이 충돌들에서 제어기는 부딪힌 저평면 상자에 관한 정보를 스캔으로도 상자 표로도 얻지 못하였다. 다만 이는 정보가 없었음을 보일 뿐이며, 정보가 있었다면 충돌을 피하였을지는 시험하지 않았다.

#### 3.2 회차 루프 결과

1회차로는 모델 간 차이가 드러나지 않으므로, gpt-oss-120b가 2.3절의 회차 루프에서 몇 회차 만에 통과하는지를 측정하였다. 가속기마다 트랙 A 5표본과 트랙 B 1표본을 수행하여 12실행 93회차(GPU 45, NPU 48)를 얻었다. 트랙 B 표본은 각 가속기에서 gpt-oss-120b의 1회차 트랙 B 5건 중 저평면 충돌을 낸 유일한 표본이다.

통과는 GPU 트랙 A의 한 실행이 5회차에 거둔 1건뿐이다. 93회차의 판정은 가시 충돌 39, 정지 23, 저평면 충돌 22, 정적 실격 7, 실행 오류 1, 통과 1회였다. 정적 실격 7회는 모두 수정 구역 밖의 문장부호를 유니코드 문자로 바꿔 쓴 경우였다. 통과 실행은 접촉(3회차), 위치(4회차), yaw(5회차) 조건을 차례로 해소하였다. 같은 코드를 8회 재채점한 판정은 모두 통과였다. 하네스는 실행마다 비트 단위로 같은 결과를 내지 않아, 최종 거리와 도달 시각은 vLLM이 같은 GPU에 상주한 5회와 Isaac Sim만 실행한 3회 모두에서 두 값(0.6967 m·56.417 s 또는 0.7048 m·56.100 s) 중 하나로 나타났다. 허용치 대비 여유는 0.045–0.053 m였다. 재채점 8회 중 원시 기록(결과 파일 또는 실행 로그)이 남은 것은 두 값에 1회씩 2회이며, 나머지 6회는 실험 노트의 기록이다. 이 코드는 피드백이 알려 준 충돌 대상(상자 06)의 좌표를 상자 표에서 옮겨 우회 경유점을 하드코딩한 것이다. 주석은 이 상자를 'large central box'로 부를 뿐, 높이 0.18 m를 스캔 평면과 연결하지 않았다.

상한을 30회차로 둔 NPU 별도 1실행(1회차만 공유, 상한 8 결과와 합산하지 않음)도 통과하지 못하였다. 최종 거리가 가장 가까웠던 24회차에도 13.94 m였다. 피드백 필드를 줄인 GPU 절제 실험(2조건 × 5표본, 새 생성 70회차)에서도 통과는 10실행 중 0실행이었다.

1회차와 상한 8 루프의 트랙 A 응답 90건(1회차 30건, 2회차 이후 60건)과 상한 30 실행의 응답 29건(독립 표본 아님)의 코드와 추론을 각각 수동으로 판정하였다. 상한 8 루프의 나머지 7건은 기록 손실로 원문이 없다. 1회차·상한 8 응답 90건 중 상자 높이와 스캔 평면을 연결한 응답은 없었고, 상한 30 응답 29건 중 1건(30회차)은 상자 13의 높이(0.2 m)를 스캔과 연결하였으나 스캔에 검출된다고 잘못 결론지었다. 표 3의 Claude 행은 같은 입력·피드백 문구와 상한 8로 수행한 동일 입력 실행이다(2.4절, 4장).

#### 3.3 가속기별 비교

같은 이름의 모델을 GPU 1장과 NPU 4장 구성에서 서빙하여(가중치 해시 확인은 Qwen3만) 결과와 지연을 비교하였다(표 4). 카드 수가 다르므로 모든 비교는 구성 단위이다. 두 가속기의 표본은 seed로 짝지을 수 없으므로 분포로만 비교한다. 1회차는 양쪽 모두 30건 중 통과 0건이며, 실패 분포(표 3)도 구별되지 않았다. 실행 오류 2건은 NPU의 EXAONE 한 셀에서 나왔으므로 가속기 특성으로 일반화하지 않는다. 회차 루프에서는 GPU 6실행 중 1실행이 통과하고 NPU는 통과가 없었으나, 트랙 A 5실행 중 1 대 0의 차이여서 가속기 효과로 해석할 수 없다. 저평면 충돌(GPU 13회, NPU 9회)과 문장부호 치환에 의한 정적 실격(GPU 4회, NPU 3회)은 양쪽에서 반복되었다.

요청 단위 처리량은 gpt-oss-120b에서 GPU가 6.3배, EXAONE에서 1.1배 높았고 Qwen3에서는 NPU가 1.25배 높아, 우열이 모델에 따라 뒤집혔다. 출력 토큰 수의 가속기 간 비는 0.97~1.02였다. 회차 지연 중앙값의 차이(63.0 s 대 115.1 s)는 물리 실행이 아니라 생성 시간에서 왔다. 정리하면 통과 여부에서는 가속기 간 차이가 구별되지 않았고, 구성 단위의 반복 주기는 달랐다.

GPU 구성에서는 생성 서버와 Isaac이 같은 카드를 사용하였다.

### 4. 코딩 에이전트 작업 절차 분석

#### 4.1 동일 입력 실행의 작업 절차

Claude 에이전트는 1회차에 정적 검증과 물리 실행을 모두 통과하였다(최종 거리 0.1018 m, yaw 오차 0.0287 rad, 접촉 0, 도달 39.75 s). 1회차에 90분 동안 출력 305,106 토큰(그중 사고 227,362)을 냈다. 도구는 98회(Bash 64, Read 20, Edit 10, Write 2, 기타 2) 호출하였고, 서브에이전트와 외부 피드백은 쓰지 않았다. 표 5는 기록을 여섯 단계로 나눈 것이다.

첫 20분은 대부분 숙고였다. 첫 도구 호출(13분) 전까지 출력 77,846 토큰을 냈고, 20분까지 도구는 파일 탐색과 기반 파일 저장 3회뿐이었다. 20분에 나온 첫 초안의 머리 주석에는 "Four boxes are lower than the default z=0.35 scan plane, so they are known only from MISSION"(상자 4개는 기본 스캔 평면보다 낮아 MISSION으로만 알 수 있다)이라는 판단이 이미 있었고, 초안은 상자 14개를 모두 지도에 넣었다. 결정적 판단이 시험보다 앞선 것이다. 이어 만든 자작 시뮬레이터는 상자를 높이 범위가 있는 직육면체로 두고, 스캔 광선이 높이 z를 지나는 물체만 맞히도록 구현하였다. 즉 시뮬레이터가 앞서 읽어 낸 명세를 담았으므로, 그 위의 시험은 스캔 평면 아래 물체를 놓치는 제어기를 실패로 판정할 수 있었고, 실제로 에이전트가 지어 넣은 낮은 팔레트·선반 하단 빔과의 충돌을 드러냈다. 에이전트는 numpy로 PNG 렌더러를 직접 작성해 궤적 그림을 확인하고, 고정 28개·무작위 80개 시나리오를 모두 접촉 없이 통과시켰다(108/108, 47분). 이후 코드를 고치며 늘린 회귀 시험에서 실패한 무작위 시드마다 실패를 재현하고 경로 존재를 확인하여 원인을 가렸다. 제출 파일은 수정 구역을 기반 파일에 끼워 넣고 구역 밖을 바이트 단위로 대조하여 만들었다.

#### 4.2 절차 요인의 이식 설계

옮기는 것은 절차이며 내용이 아니다. "상자 표를 지도 제약으로 쓴다"는 결론이나 높이를 반영한 센서 모델을 전하면 정답 누설이다. 그래서 표 5의 단계 중 내용 없이 옮길 수 있는 요소를 NPU의 gpt-oss-120b에 한 겹씩 더하는 조건을 두었다. 회차 루프의 NPU 트랙 A 5실행을 기준 T0로 둔다. 각 이식 조건의 첫 메시지·정적 검증·물리 실행·피드백 문구·상한 8회차·샘플링은 T0와 같다.

- T3(숙고, 단계 ①): T0에 요청 필드 reasoning_effort=high를 더한다. T0의 1회차는 1회차 실험의 응답을 재사용했고, T3는 1회차부터 호출당 16,384 토큰 한도로 새로 생성하였다. 사전 점검에서 같은 NPU 서버의 추론 토큰이 약 2.5배로 늘어 적용됨을 확인하였다(282~456 → 774~1,163). 표본 5.
- T2(자기 검증 도구, 단계 ③~⑥의 수단): T3에 Python 실행 도구와 그 사용을 알리는 시스템 안내 1문단(292자)을 더한다. 코드는 네트워크가 없는 격리 환경의 빈 작업 폴더에서 실행되며, 회차당 도구 12회·60분 상한이다. 대화는 6만 자 절단 대신 오래된 도구 출력·코드를 줄여 30만 자 안에 맞춘다. 표본 3.
- T2P(작업 순서 지시, 단계 ①~⑥): T2의 시스템 안내 대신, 에이전트가 지시 없이 한 작업 순서를 담은 11단계 지시문(12,322자)을 시스템 메시지로 준다. 정답에 해당하는 판단·지도 해법·높이별 센서 모델·벽 위치는 누설 감사로 제외하였다. gpt-oss-120b는 그림을 읽지 못하므로 궤적 그림 확인은 텍스트 출력으로 바꾸었다. 작업 폴더에 기반 파일 원문을 두고 회차당 도구 28회·6시간, 호출당 출력 24,576 토큰을 허용하며(대화 25만 자), 그 회차에 시험 기록·최종 확인·제출 파일이 없으면 하네스가 최종 답을 한 번 반려하고 필수 파일을 만들도록 안내한다. 표본 3.

T2P는 지시문과 함께 도구 예산·출력 한도·기반 파일 원문 제공·최종 답 반려 안내가 바뀐 묶음 조건으로 해석한다. 에이전트 하네스에서 모델만 바꾸는 조건(T1)은 당시 NPU의 요청 단위 처리량(약 10 tok/s)으로 회차당 수 시간이 예상되어 후속 과제로 둔다. 각 조건이 덧붙이는 문구는 원문을 기록하고, 상자 높이·스캔 평면 값·"검출되지 않는다" 류의 귀결·상자 번호가 없는지 실행 전에 감사하였다. 실행은 2026년 10월 6~7일에 하였다. 통신 단절·요청 시간 초과·실행 스크립트 결함으로 판정 전에 끊긴 생성은 같은 상태에서 다시 생성하였고, 버린 생성물은 결과로 세지 않았다. 판정이 끝난 회차는 그대로 두었다.

#### 4.3 이식 결과

숙고 조건(T3)은 5회 중 1회 통과하였고(8회차, 최종 거리 0.45 m, 접촉 0, 도달 33.7 s), 숙고+도구 조건(T2)과 작업 순서 지시 조건(T2P)은 각각 3회 중 0회였다(표 6). 표본이 작으므로 통과 수의 차이를 요인의 효과로 단정하지 않는다. Claude 행은 T0와 하네스·도구·사고 예산이 함께 다르므로 직접 맞대지 않는다.

숙고는 회차당 추론 토큰 중앙값을 541에서 7,431로(둘 다 2–8회차) 약 14배 늘렸으나, 응답 33건 중 상자 높이와 스캔 평면을 올바르게 연결한 응답은 0건이었다. 늘어난 추론은 출력 한도도 압박하였다. 두 실행은 출력 한도(16,384 토큰)에 걸린 응답이 본문 없이 반환되어, 2.3절의 규칙에 따라 3회차와 6회차에 끝났다. 통과한 실행은 4회차에 상자 표 14개 전체로 격자 지도를 만들어 A*로 경로를 계획하였다가, 지게차에 충돌한 뒤 반응형 회피로 돌아갔다. 6회차에 저평면 상자 04에 충돌하자 7회차에 같은 지도 계획을 다시 택하였고, 경유점 접근 감속을 없애고 속도를 높인 8회차에 통과하였다. 이 실행의 추론 어디에도 높이와 스캔 평면의 관계는 없었다. 단계 ①의 숙고가 단계 ②의 판단을 낳지 못한 채, 해법 구조에는 충돌 피드백을 거쳐 도달한 것이다.

숙고+도구 조건(T2)에서 도구는 24개 회차 중 5개 회차에서 모두 8회 쓰였다. 구문 확인이나 가짜 스캔값을 넣은 1~10 스텝 단위 시험이었고 2회는 인자·구문 오류로 실행되지 않았다. 자세를 적분한 것은 장애물 없는 10 스텝(약 0.17 s) 1건뿐이었고, 상자 배치를 담은 시험은 없었다. 도구를 주는 것만으로는 단계 ③~⑤가 일어나지 않았다.

작업 순서 지시 조건에서는 도구가 24회차 모두에서 394회(회차당 중앙값 15회) 쓰였다. 단계별 이행은 표 5의 오른쪽 열과 같다. 설계 메모와 조립 스크립트는 세 실행 모두 만들었으나, 시뮬레이터 파일은 두 실행만 만들었고 둘 다 상자를 높이 없는 2D 사각형으로 넣었다. 스캔 함수는 z 인자를 받기만 하고 쓰지 않았으며, 한 실행은 "For simplicity, ignore z"라고 주석을 달았다. 이 파일을 실행한 2회는 모두 오류로 끝났고, 출발부터 끝까지 주행을 돌린 것은 도구 호출 코드 안에 따로 쓴 2D 시뮬레이션 2회(두 실행 각 1회)뿐이었다. 고정·무작위 시험 묶음은 만들어지지 않았다. 필수 파일 없이 최종 답을 내어 반려 안내를 받은 회차가 16, 도구 28회를 다 써 최종 답을 강제당한 회차가 7이었다. 정적 실격은 6회로 늘었다. 4회는 그 회차의 제출 파일을 저장하지 못한 경우였고, 2회는 지시와 달리 파일 전문을 답으로 다시 써서 생긴 문장부호 치환이었다. 높이와 스캔 평면을 올바르게 연결한 응답은 없었다. 가장 가까운 응답도 높은 상자에 대해서만 둘을 비교하거나, '낮은 장애물은 못 볼 수 있다'는 가설을 다른 가설과 함께 스쳐 지나가는 데 그쳤다.

두 실행 계열을 단계별로 맞대면, T2P에서는 단계 ④·⑤가 일어나지 않았고(시험 묶음 0, 재현 기록 0) 단계 ③의 시뮬레이터도 높이를 버린 2D였다. 차이는 단계의 유무와 내용 모두에 있었다. 에이전트의 시뮬레이터는 단계 ②에서 읽어 낸 명세(상자 높이와 스캔 높이)를 담아, 스캔 평면 아래 물체와의 충돌을 실패로 드러낼 수 있었다. 다만 저평면 상자 처리는 시뮬레이터 이전의 첫 초안에 이미 있었고 표본이 1건이어서, 이 검증이 통과에 얼마나 기여했는지는 가릴 수 없다. T2P의 시뮬레이터는 같은 순서의 지시 아래 만들어졌으나 높이를 단순화하여 버렸으므로, 그 위에서는 시험을 몇 번 돌려도 스캔이 낮은 상자를 놓쳐 생기는 충돌이 재현될 수 없었다. 메모·조립·도구 호출 같은 절차의 일부 형식은 옮겨졌지만, 명세를 담은 검증 환경은 명세를 읽어 낸 판단이 없던 실행에서는 만들어지지 않았다. 유일한 통과(T3)도 이 절차가 아니라 물리 실행 피드백을 거친 탐색에서 나왔다.

| T2 숙고 + 자기 검증 도구 | 0/3 | — | 398.6 (237.0~1,609.8) | 0 (0~3) |
| T2P 작업 순서 지시 | 0/3 | — | 1,460.4 (327.4~3,723.3) | 15 (1~28) |
| Claude 동일 입력 | 1/1 | 1 | 5,393 (1회차) | 98 |

주: 시간과 도구 호출은 회차당 중앙값(최소~최대)이다. T0는 NPU 트랙 A 2–8회차 35건 기준이다(표 4의 NPU 생성 시간은 트랙 B를 포함한 42회차). Claude의 시간은 회차 안의 도구 실행을 포함한다. T3·T2는 요청 단위 처리량이 6~29 tok/s로 변한 시기에, T2P는 그 뒤에 측정하여 T0와 시간을 맞대지 않는다. T2·T2P의 생성 시간은 회차 안 모델 호출의 합이다. 회차 판정(통과·저평면·가시·정지·오류·정적 실격·빈 응답)은 T0 0·7·18·11·1·3·0(40회차), T3 1·4·14·11·0·1·2(33회차), T2 0·8·4·11·0·1·0(24회차), T2P 0·2·9·5·2·6·0(24회차)이다. T3의 가시 충돌 14회에는 지게차 충돌 2회가 포함된다. Claude는 외부 API로 생성하므로 그 시간을 가속기 비교에 쓰지 않는다.

## Ⅲ. 결 론

본 논문은 GPU·NPU에서 서빙한 공개 가중치 LLM이 작성한 로봇 제어 코드를 물리 시뮬레이션으로 판정하였다. 3개 모델의 1회차 60건은 정적 검증을 모두 통과하였으나, 물리 실행에서는 GPU·NPU 각 30건 중 통과가 한 건도 없었다. 회차 루프(상한 8)에서 gpt-oss-120b는 GPU에서 6개 실행 중 1개만 5회차에 통과하였다. NPU에서는 6개 실행 48회차와 상한을 30회차로 둔 별도 1실행 모두 통과하지 못하였다. 통과 여부와 실패 유형 분포에서는 가속기 간 차이가 구별되지 않았다. 1회차와 상한 8 루프의 트랙 A 응답 90건 중 상자 높이와 스캔 평면을 연결한 응답은 0건이었고, 상한 30 별도 실행의 29건 중 1건은 상자 높이를 스캔과 연결하였으나 검출된다고 잘못 판단하였다. 정보가 입력에 있었는데도 응답이 이를 연결하지 못한 것이다.

같은 입력을 받은 Claude Code 에이전트(claude-opus-5-5)는 1회차에 통과하였다(1회 중 1회). 작업 절차를 분해하면 결정적 판단은 시험 전에 쓴 첫 초안에 이미 있었고, 그 판단을 담은 자작 시뮬레이터와 108개 상황 시험이 코드를 다듬었다. 절차 요인을 NPU 서빙 gpt-oss-120b에 이식한 결과 숙고 조건은 5회 중 1회(8회차, 최종 거리 0.45 m) 통과하였다. 숙고+도구 조건과 작업 순서 지시 조건은 각각 3회 중 0회였다. 통과한 실행도 상자 높이와 스캔 평면을 연결하지 않은 채 충돌 피드백을 거쳐 표 기반 지도에 도달하였다. 작업 순서를 지시하자 도구 사용은 크게 늘었으나, 시뮬레이터는 높이를 버린 2D였고 시험 묶음은 만들어지지 않았다. 따라서 이번 표본에서 옮겨진 것은 설계 메모·조립·잦은 도구 호출 같은 절차의 일부 형식이었고, 시험 묶음, 그리고 명세를 담은 자기 검증 환경은 옮겨지지 않았다. 이 결과는 단계를 지시하는 것만으로는 부족하며, 정답 누설 없이 명세를 충실히 담은 검증 환경을 갖추게 하는 방법을 다룰 필요가 있음을 시사한다.

본 연구는 단일 주행 환경에서 수행되었고, 조건당 표본이 5개 이하로 작다. 제어기의 감각은 잡음 없는 가상 스캔과 참값 자세로 이상화되어 있어, 실제 센서 데이터 처리와 위치 추정은 다루지 않았다. 회차 루프 실험은 gpt-oss-120b 한 모델에 한정되며, 에이전트 실행은 1건이다. Claude 실행은 입력만 같을 뿐 시스템 프롬프트·도구·사고 예산이 다르므로 모델 단독 비교로 해석하지 않는다. 이식 조건의 생성 시간은 시기에 따라 달랐다(요청 단위 처리량 6~29 tok/s). 숙고 조건의 두 실행은 출력 한도에 걸린 응답이 본문 없이 반환되어 상한보다 적은 회차(3회, 6회)만 사용하였다. 작업 순서 지시 조건은 지시문과 함께 도구 예산·출력 한도·기반 파일 원문 제공·최종 답 반려 안내가 바뀐 묶음 조건이며, 정답 누설을 막기 위해 에이전트 시뮬레이터의 결정적 요소(높이별 센서 모델)를 옮기지 않았다. 또한 하네스의 스캔은 PhysX가 먼저 보고한 적중면에서 탐색을 멈추므로, 상자에서 떨어진 빈 바닥 1,552곳에서 쏜 빔 94,672개 중 2.6%가 가장 가까운 면보다 먼 거리(초과분 중앙값 0.92 m)를 돌려주었다. 가장 가까운 면은 대부분 창고 건물·선반·지게차였으나 상자인 빔도 244개였고, 여기에는 가시 충돌의 주 상대인 상자 00·01이 포함된다. 이 성질은 모든 조건에 같게 적용되었으나, 가시 충돌의 일부는 스캔이 부딪힌 상자보다 먼 면을 돌려준 상황에서 일어났을 수 있다.

향후에는 로봇 모델에 실린 2D·3D 라이다와 카메라의 실제 데이터, 센서 기반 위치 추정을 제어기에 주어 같은 분석을 반복한다. 또한 정답을 누설하지 않으면서 명세를 담은 검증 환경을 제공하는 조건과, gpt-oss-120b를 에이전트 하네스에 넣어 모델만 바꾸는 조건(T1)을 더 많은 표본으로 시험하여, 작업 절차의 어느 요소가 공개 모델의 물리 실행 통과로 이어지는지 확인할 계획이다.

(An Analysis of LLM Robot-Control Code Generation in Physics Simulation and of a Coding Agent's Work Procedure)

**Abstract :** 대규모 언어 모델(LLM)이 생성한 로봇 제어 코드는 코드 수준 검사를 통과해도 물리 환경에서 실패할 수 있다. 본 논문은 Nova Carter 로봇의 60 Hz 제어 함수를 작성하는 주행 과제와, 생성 코드를 정적 검증과 Isaac Sim 물리 실행으로 판정하는 평가 환경을 구축하였다. 상자 14개 중 4개는 거리 센서의 기본 스캔 평면(0.35 m)보다 낮으며, 상자 높이와 스캔 높이는 모두 입력에 주어진다. GPU와 NPU에서 서빙한 공개 가중치 모델 3종의 1회차 코드 60건은 정적 검증을 모두 통과하였으나 물리 실행 통과는 0건이었고, 판정을 되돌려주는 회차 루프에서도 gpt-oss-120b는 12개 실행 중 1개만 통과하였다. 상자 표 사용을 허용한 1회차·회차 루프 응답 90건 중 상자 높이와 스캔 평면을 연결한 응답은 없었다. 같은 입력을 받은 코딩 에이전트 Claude Code는 1회 실행에서 1회차에 통과하였다. 에이전트는 시험 전 첫 초안에서 이미 낮은 상자가 기본 스캔 평면 아래라 상자 표로만 알 수 있다고 판단했고, 이어 높이를 반영한 자작 시뮬레이터로 108개 상황을 시험하였다. 이 절차의 요소를 NPU 서빙 gpt-oss-120b에 이식하자 숙고 조건은 5회 중 1회 통과하였으나, 높이와 스캔을 연결하지 않고 충돌 피드백으로 도달한 것이었다. 숙고+도구 조건과 작업 순서 지시 조건은 각각 3회 중 0회였다. 작업 순서를 지시하고 도구 예산을 늘리자 도구 호출은 숙고+도구 조건의 약 50배가 되었으나, 시뮬레이터는 높이를 버린 2D였고 시험 묶음은 만들어지지 않았다. 절차의 일부 형식은 옮겨졌으나 명세를 담은 자기 검증 환경은 옮겨지지 않았다.

**Keywords :** 대규모 언어 모델, 로봇 제어 코드 생성, 물리 시뮬레이션, 코딩 에이전트, 신경망 처리 장치(NPU)

## Ⅰ. 서 론

LLM이 자연어 지시로부터 로봇 제어 코드를 생성하는 접근이 확산되고 있다[1]. 생성 코드는 흔히 구문·규약 같은 코드 수준 검사로 평가되지만, 제어 코드의 성패는 센서의 특성과 접촉이 작용하는 물리 환경에서 실행해야 드러나며, 이를 판정하는 데 Isaac Sim[2] 같은 물리 시뮬레이터를 쓸 수 있다.

한편 코딩 에이전트는 숙고하고 파일을 만들어 실행하며 스스로 시험한 뒤 제출하는 작업 절차를 거친다. 같은 과제에서 에이전트는 통과하고 단일 호출 모델은 실패한다면, 절차의 어느 요소가 그 차이를 만드는지가 질문이 된다. 데이터를 외부로 보내지 않으려고 공개 가중치 모델을 GPU(vLLM[3])나 NPU(RNGD[4])에서 서빙하는 임베디드·로봇 현장에서 이는 서빙 모델에 에이전트의 절차를 옮길 수 있는가의 문제이기도 하다. 본 논문의 기여는 다음과 같다.
- 낮은 장애물 판단에 필요한 정보(상자 높이와 스캔 높이)를 입력에 모두 공개한 주행 과제와, 정적 검증·물리 실행을 나눈 평가 환경을 구축하였다.
- GPU·NPU에서 서빙한 공개 가중치 모델 3종의 생성 코드를 물리 실행으로 판정하여 정적 검증과의 간극과 명세 연결의 부재를 측정하였다.
- 코딩 에이전트의 작업 절차를 단계로 분해하고 공개 모델에 한 겹씩 이식하여, 옮겨진 요소와 그렇지 않은 요소를 보였다.

## Ⅱ. 본 론

### 1. 과제와 평가 환경

과제는 Isaac Sim 창고 장면에서 차동 구동 로봇 Nova Carter를 남서 모서리 (−9.0 m, −10.8 m)에서 북동 모서리 (8.0 m, 16.5 m)까지 주행시키는 것이다(그림 1(a)). 모델은 기반 파일(base_carter_run.py)의 수정 구역에 제어 함수 controller(t, pose, env) → (v, w, done)을 작성한다. 제어기의 감각은 참값 자세와 env.raycast_scan()뿐인데, 후자는 기본값으로 높이 z = 0.35 m의 수평면에서 전방 180°에 광선 61개를 쏘는 잡음 없는 가상 2D 거리 센서(PhysX 광선 질의)이며 z는 인자로 바꿀 수 있다. 로봇의 라이다·카메라 데이터는 주지 않는다. 120 s 안에 목표에서 0.75 m·yaw 0.26 rad 이내로 멈추고 상자·지게차·선반과 접촉하지 않으면 통과이다.

기반 파일의 상자 표(MISSION)는 상자 14개의 위치·크기·높이를 명시한다. 상자 04·05·06·13은 높이 0.18~0.25 m로 기본 스캔 평면보다 낮다(저평면 장애물, 그림 1(b)). Isaac Sim에서 각 상자의 1 m 밖에서 z = 0.35 m 광선을 쏘면 높이 1.0 m 상자 10개는 모두 검출되고 저평면 장애물 4개는 하나도 검출되지 않는다. 목표 방향을 막는 상자 03의 동쪽 우회로를 상자 04·05가 막지만 0.6 m 여유로 지나는 34.7 m 경로가 있다. 상자 높이와 스캔 높이가 입력에 평문으로 있어 대소 비교만으로 귀결이 나오므로 은닉 정보가 아니며, 저평면 장애물을 알고 피하려면 상자 표를 지도로 쓰거나 스캔 높이를 낮춰야 한다. 주 실험은 상자 표 사용을 허용하는 트랙 A이고, 상자 표 참조와 좌표 하드코딩을 금지하는 트랙 B는 보조이다.

생성 코드는 정적 검증(구문, 수정 구역 밖 바이트 동일성, 트랙 B 규칙, controller() 정의)을 거쳐 Isaac Sim 4.5.0에서 직렬로 물리 실행한다. 트랙 B 규칙(상자 표·배치 참조와 좌표 쌍 4개 이상의 상수 금지)은 실험 전에 정하였고, 수정 구역만 출력한 응답은 기반 파일에 끼워 넣어 검사한다. 실패하면 같은 대화에 판정 결과를 덧붙여 재제출을 받는다(회차 루프, 상한 8회차; 정적 실격·실행 오류도 한 회차로 세고 빈 응답이면 실행 종료). 모델 3종(gpt-oss-120b, Qwen3-32B-FP8, EXAONE-4.0-32B-FP8)은 GPU(RTX PRO 6000 1장, vLLM 0.29.0)와 NPU(RNGD 4장, furiosa-llm 2026.3.0)에서 같은 모델명으로 서빙하였고(가중치 해시 확인은 Qwen3만), 입력은 트랙 프롬프트와 기반 파일을 담은 메시지 하나이며 시스템 프롬프트와 도구는 없다(temperature 0.7, top_p 0.95).

에이전트 조건은 Claude Code 2.1.291(모델 claude-opus-5-5)에 트랙 A의 같은 입력을 주어, 빈 작업·임시 폴더와 읽기 전용 시스템 디렉터리만 보이는 격리 환경에서 기본 도구(파일, 셸; 웹·MCP 차단)로 실행하였다(채점·피드백·상한 동일). 도구·사고 예산이 달라 모델 비교가 아니라 절차 관찰에 쓰며, 이벤트 기록·작업 파일로 절차를 재구성하였다(사고 본문 미기록). 표본은 1건이며, 앞선 시작 2회는 제출 없이 끊겨(세션 재시작, 사용 한도) 무효로 하였다.

### 2. 물리 시뮬레이션 판정 결과

1회차 60건(모델·가속기당 트랙 A·B 각 5건)은 정적 검증을 모두 통과하였으나(21건은 끼워 넣은 뒤 검사) 물리 실행 통과는 0건이었다(표 1). 실패는 저평면 충돌 10, 가시 충돌 35(대부분 경로 초반의 상자 00·01), 정지 13, 실행 오류 2건이었다(접촉 상대 기준, 표 1 주). 1회차·상한 8 루프(2회차 이후)·이식 조건(4절)의 저평면 충돌 42건(각 10·18·14건) 중 원문이 남은 41건은 모두 상자 표·좌표 없이 기본 높이의 스캔만 호출하여, 부딪힌 저평면 장애물의 정보를 얻지 못하였다(정보가 있었다면 피하였을지는 시험하지 않았다).

회차 루프(gpt-oss-120b, 가속기당 트랙 A 5·트랙 B 1실행, 93회차)에서 통과는 GPU 트랙 A의 1실행(5회차)뿐이었다. 트랙 B 실행에는 가속기마다 1회차 트랙 B 5건 중 저평면 충돌을 낸 유일한 표본을 썼다. 통과한 코드도 피드백이 알려 준 충돌 상자(상자 06)의 좌표를 상자 표에서 옮겨 경유점으로 하드코딩했을 뿐 높이와 스캔을 연결하지 않았다. 정적 실격 7회는 모두 수정 구역 밖 문장부호를 유니코드 문자로 바꾼 경우였고, 상한 30회차의 NPU 별도 1실행은 통과하지 못하였다. 1회차와 상한 8 루프의 트랙 A 응답 중 원문이 남은 90건을 수동 판정한 결과 상자 높이와 스캔 평면을 연결한 응답은 없었다(상한 30의 29건 중 1건은 연결했으나 검출된다고 잘못 판단).

가속기 간에는 1회차 실패 분포와 회차 루프 통과(트랙 A 5실행 중 1 대 0)가 구별되지 않았다. 요청 단위 처리량(출력 토큰 ÷ 요청 시간, 1회차 10건 중앙값)은 gpt-oss-120b에서 GPU가 6.3배, Qwen3에서 NPU가 1.25배 높았다(1장 대 4장의 구성 단위 비교).

### 3. 코딩 에이전트의 작업 절차

Claude는 1회차에 통과하였다(최종 거리 0.10 m, 접촉 0, 도달 39.75 s; 90분, 도구 98회, 서브에이전트 0). 표 2는 기록을 여섯 단계로 나눈 것이며, 오른쪽 열은 4절 작업 순서 지시(T2P)의 단계별 이행이다. 첫 도구 호출(13분)까지 출력 77,846 토큰을 냈고, 20분의 첫 초안 머리 주석에 이미 "Four boxes are lower than the default z=0.35 scan plane, so they are known only from MISSION"이라는 판단이 있었다. 이어 만든 자작 시뮬레이터는 상자 높이와 스캔 높이를 반영하여 저평면 장애물을 놓치는 제어기를 실패로 판정할 수 있었다. 에이전트는 108개 상황을 모두 통과시킨 뒤 상황을 늘린 회귀 시험에서 실패 사례의 원인을 가렸고, 수정 구역을 기반 파일에 끼워 넣어 바이트 대조로 제출하였다.

### 4. 절차 요인의 이식

옮기는 것은 절차이며 내용이 아니므로, 결론("상자 표를 지도로")과 높이별 센서 모델은 정답 누설로 보고 뺐다. 기준 T0(회차 루프의 NPU 트랙 A 5실행)에 요소를 한 겹씩 더하였다. T3(숙고, 단계 ①)은 reasoning_effort=high(5실행)이고, T2(자기 검증 수단, ③~⑥)는 T3에 Python 실행 도구와 안내를 더한다(회차당 도구 12회, 3실행). T2P(작업 순서, ①~⑥)는 T2의 안내 대신 에이전트의 작업 순서를 담은 11단계 지시문(12,322자)과 기반 파일 원문, 회차당 도구 28회·6시간을 주고, 시험 기록·최종 확인·제출 파일 중 하나라도 그 회차에 갱신되지 않았으면 최종 답을 한 번 반려한다(3실행). T2P는 지시와 예산이 함께 바뀐 묶음 조건이며, 덧붙인 문구는 실행 전에 누설 감사를 거쳤다.

| ⑥ 조립 (89~90분) | 끼워 넣기·바이트 대조 | 스크립트 3/3, 정적 실격 6 |

T3은 5회 중 1회(8회차) 통과하였고 T2·T2P는 각각 3회 중 0회였다(표 3). 표본이 작아 차이를 요인의 효과로 단정하지 않는다. T3은 추론 토큰을 약 14배로 늘렸으나 높이와 스캔을 연결한 응답은 없었고, 두 실행은 출력 한도에 걸린 빈 응답으로 3·6회차에 끝났으며, 통과한 실행은 충돌 피드백을 거쳐 상자 표 기반 지도에 도달하였다. T2에서 도구는 24개 회차 중 5개 회차에서 8회 쓰였고 상자 배치를 담은 시험은 없었다. T2P에서는 도구 호출이 394회로 늘었으나 시뮬레이터 파일을 만든 두 실행은 상자를 높이 없는 2D로 넣었고(한 실행의 주석: "For simplicity, ignore z") 그 파일의 실행 2회는 모두 오류였다. 최종 답은 24개 회차 중 16개에서 반려되었고, 정적 실격 6회 중 4회는 제출 파일을 저장하지 못한 경우였다.

에이전트와 T2P를 단계별로 맞대면(표 2) 차이는 단계의 유무와 내용 모두에 있었다. 메모·조립·도구 호출 같은 형식은 옮겨졌지만, 명세를 읽어 낸 판단이 없던 실행은 명세를 담은 검증 환경을 만들지 못했고, 높이를 버린 시뮬레이터로는 저평면 장애물을 놓치는 충돌을 재현할 수 없었다. 다만 에이전트의 저평면 판단은 시뮬레이터보다 먼저 있었고 표본이 1건이어서 그 검증의 기여는 가릴 수 없으며, 유일한 통과(T3)도 피드백을 거친 탐색에서 나왔다.

## Ⅲ. 결 론

본 논문은 공개 가중치 LLM이 작성한 로봇 제어 코드를 물리 시뮬레이션으로 판정하여, 정적 검증을 모두 통과한 1회차 코드 60건이 물리 실행에서는 한 건도 통과하지 못하였고 1회차와 상한 8 루프의 트랙 A 응답 90건 중 상자 높이와 스캔 평면을 연결한 응답이 없었음을 보였다. 코딩 에이전트의 절차를 NPU 서빙 모델에 이식하자 설계 메모·조립·잦은 도구 호출 같은 형식은 옮겨졌으나 시험 묶음과 명세를 담은 자기 검증 환경은 옮겨지지 않았다. 이는 서빙 모델로 제어 코드를 만드는 임베디드·로봇 현장에 물리 실행 판정과, 단계 지시를 넘어 모델이 정답 누설 없이 명세를 담은 검증 환경을 갖추게 할 방법이 필요함을 시사한다.

본 연구는 단일 환경, 조건당 5실행 이하, 에이전트 1실행에 기반하며, 에이전트 실행은 도구·사고 예산이 달라 모델 비교가 아니다. T2P는 묶음 조건이고, 누설을 막기 위해 높이별 센서 모델은 옮기지 않았다. 제어기의 감각은 잡음 없는 가상 스캔과 참값 자세로 이상화되었고, 스캔 함수는 PhysX가 먼저 보고한 면을 돌려주어 빈 바닥 1,552곳에서 쏜 빔의 2.6%가 가장 가까운 면보다 먼 거리를 반환하였다. 그중 63개는 가장 가까운 면이 가시 충돌의 주 상대인 상자 00·01이어서, 가시 충돌의 일부에 이 성질이 작용했을 수 있다. 향후에는 실제 라이다·카메라 데이터와 위치 추정을 제어기에 주어 분석을 반복하고, 모델이 정답 누설 없이 명세를 담은 검증 환경을 갖추게 하는 조건과 공개 모델로 코딩 에이전트를 구동하는 조건을 더 많은 표본으로 시험할 계획이다.

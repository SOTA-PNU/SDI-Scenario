# 실제 센서 기반 제어 코드 생성 — 사전 준비와 LLM에게 줄 정보

작성 2026-10-08. 지금까지의 실험(v1·v2)에서 제어기는 참값 자세와 가상 스캔(`env.raycast_scan()`, PhysX 광선, z 0.35 m)만 받았다. 이 문서는 로봇 모델에 실린 실제 센서 데이터를 제어기에 주고 LLM에게 그 데이터로 주행하는 코드를 요청하기 위한 준비 목록이다. 이렇게 바꾸면 새 환경 버전(v3)이 되며, v1·v2 결과와 섞어 비교하지 않는다.

제어기는 이 가운데 아무것도 읽지 못한다. 수정 구역 밖 변경과 import 추가가 금지되어 있고, API(`env`)에도 통로가 없다.

## 2. 사전 준비 (하네스·환경 쪽)

1. **구현 위치.** 공용 하네스 `levels/common/carter_env.py`는 levels와 같이 쓰므로 건드리지 않는다. arena 전용 `ArenaHarness`를 확장한다(예: `SensorArenaHarness`).
2. **수신 경로.**
   - 하네스의 in-process ROS 노드에 센서 토픽 구독을 추가하고, 토픽마다 최신 메시지와 시각을 보관한다.
   - 지금 하네스는 물리 스텝마다 `spin_once`를 한 번만 불러 콜백을 최대 1개만 처리한다. 구독이 늘면 메시지가 밀리거나 버려진다. 스텝마다 대기 중인 콜백을 모두 비우도록(또는 별도 실행기로) 바꿔야 한다.
3. **센서 켜기.** 쓸 센서의 렌더 출력을 켠다(카메라는 대부분 꺼져 있음). 매 스텝 렌더링 비용이 늘므로 실행 속도를 먼저 잰다.
4. **형태 변환.** 제어기가 import 없이 쓸 수 있는 형태로 넘긴다.
   - 거리 배열, 점 배열(N×3), 영상 배열 등. 가능하면 차체 좌표계로 미리 변환한다(앞 2D 라이다의 180° 회전 같은 함정 제거).
   - numpy를 허용할지 정한다. 3D 점군·영상을 순수 Python으로 60 Hz에 처리하기는 어렵다. 허용하면 정적 검증 규칙도 함께 고친다.
5. **시각 동기.** 제어는 60 Hz, 센서는 더 느리다(실제 주기는 위 2번을 고친 뒤 다시 잴 것). `env`가 데이터와 함께 측정 시각·경과 시간을 돌려주게 한다.
6. **자세 정보 결정.** 둘 중 하나를 고른다.
   - 참값 자세를 유지하고 장애물 인식만 실제 센서로 바꾼다(첫 단계로 권장).
   - 참값 대신 오도메트리를 준다. 이때 잡음·드리프트를 넣지 않으면 의미가 없다.
7. **검증.**
   - 빈 base로 데이터 전달만 확인한다.
   - 실제 센서만 쓰는 참조 제어기 하나로 과제가 풀린다는 것을 보인다.
   - 상자별로 어느 센서에 잡히는지 실측한다.
     - v1 낮은 상자: 2D 라이다에는 안 잡힌다. XT32에는 약 1.2 m 밖에서 맞는다는 계산이 있으나 실측은 아직이다.
     - v2: 모든 라이다에 잡힌다.
8. **확인 필요(측정).** 센서별 실제 갱신 주기, IMU QoS, XT32 프레임당 점 수, 카메라 해상도·내부 파라미터, RTX 라이다 잡음 설정, 센서를 켰을 때의 실행 속도.

## 3. LLM에게 더 줄 정보 (base docstring의 API 문서)

지금 문서에는 참값 자세, `raycast_scan()` 서명·기본값, MISSION 표(상자 위치·크기·높이), 성공 조건만 있다. 실제 센서를 쓰게 하려면 아래를 더 적어야 한다. 원칙은 지금과 같다. 사실은 빠짐없이 주되, 결론("3D 점군으로 낮은 상자를 보라")은 주지 않는다.

| 항목 | 적을 내용 |
|---|---|
| API 서명 | 예: `env.scan_2d("front")`, `env.points_3d()`, `env.image("front_left")`, `env.odom()`; 반환 형식·자료형 |
| 탑재 위치·자세 | 센서별 차체 기준 위치(x, y, z)와 방향. 미리 변환해 넘기면 "차체 좌표계로 변환됨"이라고 적는다 |
| 측정 범위 | 2D 라이다: 360°, 3,200빔, 0.418 m 수평면, 최대 30 m. XT32: 32채널, 수직 시야. 카메라: 해상도, 화각, 내부 파라미터 |
| 단위·부호 | m, rad, 각도 증가 방향, 좌표축 정의 |
| 무효값 | -1, inf, NaN 같은 값의 뜻 |
| 시간 | 갱신 주기, 데이터 시각, 제어 주기(60 Hz)와의 관계 |
| 사각지대 | 수평 라이다는 그 높이보다 낮은 물체를 못 본다는 기하 사실은 '센서 사양'으로 적는다(높이 값만 주고 귀결은 쓰지 않는 지금 방식과 같게 할지 결정) |

## 4. 먼저 정해야 할 설계 선택

1. **상자 표를 줄 것인가.** 표를 주면 센서 없이 지도로 풀 수 있어(T3 통과 경로) 센서 인식이 필요 없어진다. 센서 인식을 재려면 표 없이(트랙 B처럼) 출발·목표만 주는 쪽이 맞다.
2. **어느 센서까지 열 것인가.** 2D 라이다만 / 2D + 3D / 카메라 포함. 카메라를 열면 numpy 허용과 실행 속도 문제가 같이 온다.
3. **상자 높이 v1 대 v2.**
   - v1(낮은 상자)이면 "3D 점군을 바르게 처리하는가"가 과제가 된다.
   - v2이면 2D 라이다만으로도 모두 보인다.
4. **참값 자세 유지 여부**(위 2-6).
5. **비교 대상.** 같은 모델로 v1(가상 스캔)과 v3(실제 센서)를 돌려야 "센서가 바뀌면 무엇이 달라지는가"를 말할 수 있다.

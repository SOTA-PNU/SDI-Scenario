LLM이 생성한 로봇 제어 코드의 물리 시뮬레이션 평가와 코딩 에이전트 작업 절차 분석
(Evaluating LLM-Generated Robot-Control Code in Physics Simulation and Analyzing a Coding Agent's Work Procedure)

Abstract : 대규모 언어 모델(LLM)이 생성한 로봇 제어 코드는 코드 수준의 검사를 통과하더라도 물리 환경에서는 실패할 수 있다. 데이터를 외부로 보내기 어려운 임베디드 및 로봇 현장에서는 공개 가중치 모델을 직접 서빙해 코드를 만들기도 하므로, 생성 코드를 어떻게 판정하고 개선할지가 중요하다. 본 연구는 Isaac Sim에서 로봇이 장애물을 피해 목표까지 주행하는 과제를 만들고, 거리 센서의 기본 스캔 높이보다 낮아 스캔에 검출되지 않는 상자를 놓았다. 상자 높이와 스캔 높이는 모두 모델 입력에 있으므로, 이 과제는 모델이 명세를 읽고 코드에 반영하는지를 평가한다. 생성 코드는 구문과 규약을 확인하는 정적 검증을 거친 뒤 물리 시뮬레이션에서 실행하여 판정하였다. GPU와 NPU에서 서빙한 공개 모델 gpt-oss-120b가 첫 시도에 낸 코드 20건은 정적 검증을 모두 통과하였으나 물리 실행에서 한 건도 통과하지 못하였고, 스캔에 검출되지 않는 상자를 알아챈 응답도 없었다. 반면 같은 입력을 받은 claude-opus-5-5 기반 코딩 에이전트는 1회 실행에서 첫 시도에 통과하였다. 작업 기록을 보면 코딩 에이전트는 초기에 낮은 상자를 파악하고, 높이를 반영한 시뮬레이터를 직접 만들어 검증하였다. 이 절차의 요소를 공개 모델에 하나씩 더하자 설계 메모나 잦은 도구 호출 같은 형식은 나타났지만 명세를 반영한 검증 환경은 만들어지지 않았고, 통과는 11회 실행 중 충돌 피드백을 거친 1회뿐이었다. 이는 공개 모델로 제어 코드를 만들 때 물리 실행을 통한 판정과 함께, 모델이 명세를 반영한 검증 환경을 스스로 갖추게 하는 방법이 필요함을 시사한다.

Keywords : 대규모 언어 모델, 로봇 제어 코드 생성, 물리 시뮬레이션, 코딩 에이전트, 신경망 처리 장치(NPU)

Ⅰ. 서 론

최근 자연어 지시로부터 로봇 제어 코드를 LLM으로 생성하는 연구가 활발하다 [1]. 생성 코드는 흔히 코드 수준의 검사로 평가되지만, 제어 코드의 성패는 센서 특성과 접촉이 작용하는 물리 환경에서 실행해 보아야 드러나는 경우가 많다. 따라서 Isaac Sim 같은 물리 시뮬레이터에서 실행하여 판정할 필요가 있다.

데이터를 외부로 보내기 어려운 임베디드 및 로봇 현장에서는 공개 모델을 vLLM[2] 기반 GPU 서버나 RNGD[3] NPU에서 직접 서빙하기도 한다. 한편 클라우드 모델 기반의 코딩 에이전트는 추론과 설계, 파일 작성과 실행, 자체 테스트를 거쳐 제출한다. 해당 에이전트만 성공한다면 어떤 절차 요소가 차이를 만들었고 이를 공개 모델에 옮길 수 있는지가 질문이다.

본 연구에서는 낮은 장애물을 판단할 정보를 모두 입력에 담은 주행 과제를 만들고, 공개 모델 gpt-oss-120b와 코딩 에이전트의 제어 코드를 물리 시뮬레이션으로 판정하였다. 또한 코딩 에이전트의 작업 절차를 이루는 요소를 공개 모델에 하나씩 더하여 주어진 임무를 완수하는 코드를 정상적으로 생성하는지 분석하였다.

Ⅱ. 본 론

1. 실험 구성

과제는 그림 1과 같이 Isaac Sim 창고 장면에서 차동 구동 로봇을 목표까지 주행시키는 것이다. 모델은 실행 틀을 갖춘 기본 코드 파일을 받아 그중 지정된 수정 구역에 60 Hz로 호출되는 제어 함수 controller(t, pose, env)를 작성한다. 제어기가 얻는 감각 정보는 시뮬레이터가 주는 로봇의 정확한 위치와 방향, 가상 2D 거리 센서 env.raycast_scan()뿐이다. 이 센서는 기본으로 높이 0.35 m 수평면에서 전방 180°에 광선 61개를 쏘며, llm은 코드를 생성할 때 원하는 높이를 지정할 수 있다. 실제 라이다와 카메라 데이터는 쓰지 않았다. 120 s 안에 목표 위치에서 0.75 m, 목표 방위에서 0.26 rad 이내로 멈추고 상자, 지게차, 선반에 닿지 않으면 통과이다.

그림 1에 번호로 표시한 상자 14개의 위치, 크기, 높이는 코드 생성 요청할 때 준 기본 코드 파일의 상자 표에 있다. 이 중 높이 0.18~0.25 m로 기본 스캔 평면보다 낮은 4개를 저평면 장애물이라 하며, 이는 2D 라이다의 사각지대를 모사한다. 각 상자의 1 m 밖에서 기본 높이로 광선을 쏘면 높이 1.0 m 상자 10개는 모두 검출되지만 저평면 장애물은 하나도 검출되지 않는다. 그러나 상자 높이와 스캔 높이가 기본 코드 파일에 있어 숨겨진 정보는 아니다. 저평면 장애물을 알고 피하려면 상자 표를 지도로 쓰거나 스캔 높이를 낮춰야 한다. 주 실험은 상자 표를 쓸 수 있는 표 허용 조건이다.

실험 환경은 표 1과 같으며, 두 가속기의 gpt-oss-120b 가중치 동일성은 확인하지 않았다.

2. 실험 방법

모델 입력은 과제 설명과 기반 파일을 담은 메시지 하나이다. 생성 코드는 구문, 수정 구역 밖 코드의 동일성, 표 금지 규칙, 함수 정의를 확인하는 정적 검증을 거쳐 물리 시뮬레이션으로 판정한다. 정적 검증은 수정 구역 밖을 바꾸거나 금지 규칙을 어긴 코드, 실행할 수 없는 코드를 시뮬레이터 실행 전에 걸러 내기 위한 것이다. 수정 구역만 낸 응답은 기반 파일에 끼워 넣어 검사하였다. 실패하면 같은 대화에 판정 결과를 덧붙여 다시 제출하게 하는 회차 루프를 두었다. 새 대화에서 시작한 회차 루프 한 번을 1회 실행이라 하며, 한 실행은 최대 8회차까지 루프가 진행된다.

코딩 에이전트에는 표 허용 조건과 같은 입력을 주어 웹 검색 등 외부 도구를 끈 격리 환경에서 1회 실행하였고, 제출 전에 중단된 실행 두 번은 제외하였다. 해당 에이전트는 모델과 도구, 계산 예산이 모두 공개 모델과 달라 성능 비교가 아닌 작업 절차 관찰에 사용하였다.

기준 조건은 NPU에서 서빙한 gpt-oss-120b의 표 허용 조건 회차 루프 5회 실행이며, 5회 모두 8회차 루프 안에 통과하지 못하였다. 여기에 코딩 에이전트의 작업 절차 요소를 다음 세 조건으로 하나씩 더하였고, 각 조건의 한 실행도 최대 8회차 루프이다. 상자 표를 지도로 쓰는 법이나 높이별 센서 모델처럼 정답에 해당하는 내용은 주지 않았으며, 추가한 문구에 정답이 들어 있지 않은지 실행 전에 점검하였다.

① 추론 강화 조건: 추론 강도를 정하는 인자 reasoning_effort를 high로 높여 5회 실행하였다.

② 도구 조건: ①에 Python 실행 도구와 그 사용 안내를 더해 3회 실행하였다.

③ 절차 지시 조건: ②의 안내 대신 코딩 에이전트의 작업 순서를 담은 11단계 지시문과 더 큰 도구 및 출력 예산을 주고, 테스트 기록 등 필수 파일을 갱신하지 않은 회차의 답은 한 번 돌려보내며 3회 실행하였다.

3. 실험 결과

표 2는 가속기별 결과이며, 충돌은 저평면 장애물에 부딪힌 저평면 충돌과 그 밖의 물체에만 부딪힌 기타 충돌로 나누었다. 1회차 코드 20건은 정적 검증을 모두 통과하고 실행 오류도 없었으나, 물리 시뮬레이션 환경에서는 모두 실패하였다. 그 중 15건은 그림 1의 경로 초반 상자 00이나 01에 부딪혔고, 저평면 충돌은 4건, 충돌 없이 목표에 못 이른 것은 1건이었다. GPU와 NPU는 실패 분포와 회차 루프 통과에 뚜렷한 차이가 없었다.

1회차 4건, 회차 루프 18건, 4절에서 다룰 세 조건 14건을 합친 저평면 충돌 36건 모두 상자 표와 좌표 없이 기본 높이 스캔만 써서 주행 중 저평면 장애물을 감지하지 못했다. 표 허용 조건의 1회차 응답 10건과 회차 루프 2회차 이후 응답 중 기록이 남은 60건, 모두 70건에서도 상자 높이를 스캔 높이와 비교한 응답은 없었다. 회차 루프에서 통과한 실행도 충돌 피드백 뒤 상자 06 좌표를 하드코딩했다.

반면 같은 입력을 받은 코딩 에이전트는 1회차에 목표에서 0.10 m 지점에 접촉 없이 도착하였다. 약 90분의 작업 기록을 보면 20분째에 쓴 첫 초안의 머리 주석에 이미 '낮은 상자 4개는 기본 스캔 평면보다 낮아 상자 표로만 알 수 있다'는 판단이 영어로 적혀 있었다. 이후 해당 에이전트는 상자 높이와 스캔 높이를 반영한 2D 시뮬레이터를 직접 만들어 108개의 상상 시나리오를 모두 통과시키고, 실패 사례를 재현하는 회귀 테스트 뒤 수정 구역을 기본 코드 파일에 끼워 넣고 그 밖을 원본과 바이트 단위로 대조해 제출하였다.

그 결과 ① 추론 강화 조건은 5회 실행 중 1회가 마지막 8회차 루프에 통과하였고, 2회는 빈 응답으로 8회차 루프 전에 끝났다. ② 도구 조건과 ③ 절차 지시 조건은 각 3회 실행 모두 통과하지 못하였다. ① 추론 강화 조건에서는 추론 토큰이 기준 조건의 약 14배로 늘었으나 상자 높이를 스캔 높이와 비교한 응답은 없었고, 통과한 실행도 충돌 피드백을 거쳐 상자 표를 지도로 쓰게 되었다. ② 도구 조건에서는 도구가 8회 쓰였으나 ③ 절차 지시 조건에서는 도구 호출이 394회로 약 50배 늘었고, 이 조건의 세 실행은 모두 설계 메모와 병합 스크립트를 만들었다. 그러나 스캔에 검출되지 않는 상자를 알아챈 응답은 없었고, 시뮬레이터 파일을 만든 두 실행은 상자를 높이 없는 2D로 넣었으며, 한 실행은 주석에 "For simplicity, ignore z"라고 적으며 높이 없는 도형을 생성했다. 이 시뮬레이터로는 저평면 충돌을 재현할 수 없고 시나리오 테스트와 회귀 테스트도 없었다.

Ⅲ. 결 론

본 연구는 LLM이 생성한 로봇 제어 코드를 물리 시뮬레이션으로 판정하고 코딩 에이전트의 작업 절차를 분석하였다. gpt-oss-120b가 1회차에 낸 코드 20건은 정적 검증을 모두 통과하고도 물리 실행에서 한 건도 통과하지 못하였고, 스캔에 검출되지 않는 상자를 알아챈 응답도 없었다. 에이전트의 작업 절차를 공개 모델에 적용하자 일부 형식은 옮겨졌으나 명세를 반영한 검증 환경은 옮겨지지 않았다. 따라서 공개 모델로 제어 코드를 만드는 임베디드 및 로봇 현장에서는 물리 실행을 통한 판정과 함께, 정답을 알려 주지 않고도 모델이 명세를 읽어 검증 환경에 반영하게 하는 방법이 필요해 보인다. 다만 본 연구는 하나의 환경과 하나의 공개 모델, 적은 표본, 이상화된 센서 입력에 기반한다. 또한 빈 바닥에서 점검한 광선의 2.6%에서 스캔 함수가 가장 가까운 면보다 먼 면의 거리를 돌려주어 기타 충돌 일부에 영향을 주었을 수 있다. 향후 실제 라이다와 카메라 데이터를 쓰고 표본을 늘려 분석을 넓힐 계획이다.
